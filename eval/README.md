# 모델 비교 평가 도구

계획: [`../docs/model-comparison-plan.md`](../docs/model-comparison-plan.md)

> ⚠ **택소노미가 두 개 있다.** Notion 정본이 감정 체계(현재 대표 12종)와 강도 척도를 교체했다(계획 §0.1).
> `labeler.html`·`quick-labeler.html`·`merge.py`·`score.py` 는 **정본(v2)** 이다. `score.py` 는 골드·예측의
> 모든 행에 `taxonomy: "v2"` 가 없거나, 감정 키가 12종 밖이거나, 강도가 1·2·3·null 밖이면 **채점을 거부한다** —
> 라벨 키가 안 겹쳐 조용히 0점이 나오는 것이 가장 위험해서다. `sample/*.json`·`challenge/boundary-gold.json`
> 과 운영 예측(`dump.py --predictions`)은 아직 **구 택소노미(v1)** 라 거부된다(재작성은 계획 §14.3).

## 무엇을 위한 것인가

**버전이 다른 모델을 같은 잣대로 비교하기 위한 것이다.** 채점기는 예측이 어디서 왔는지 모른다 —
규칙 베이스라인(V0)이든 LLM(V1)이든 KLUE-RoBERTa(V2)든, 같은 JSON 모양이기만 하면 같은 기준으로
잰다. 문서가 "모든 버전은 반드시 동일한 테스트 세트에서 평가해야 한다"고 한 것을 실행 가능하게
만드는 자리다.

그래서 **프로덕션 소스에 넣지 않는다**(계획 §11). 서비스가 아니라 실험 도구다.

## 실행

```bash
python3 score.py --gold gold.json --pred v0=pred-v0.json --pred v1=pred-v1.json
```

의존성 없음(표준 라이브러리만). 감정 목록과 가중 카파는 같은 디렉터리의 `merge.py` 에서 가져온다 —
IAA(상한)와 모델 점수가 같은 정의를 쓰게. `sample/*.json` 은 아직 v1 이라 돌지 않는다. 지금 돌려 볼 수 있는
v2 짝은 파일럿 골드다(라벨러 골드를 예측 자리에 넣으면 그 라벨러가 확정 골드와 얼마나 맞는지가 나온다):

```bash
python3 score.py --gold data/gold-pilot-agreed.json \
  --pred A=data/gold-pilot-A.json --pred B=data/gold-pilot-B.json --per-emotion A
```

옵션:

| 옵션 | 뜻 |
|---|---|
| `--pred 이름=경로` | 버전 예측. 여러 번 줄 수 있다 |
| `--set natural\|challenge\|stratified` | 골드의 `set` 으로 거른다 (`stratified` = AI Hub 층화 표본) |
| `--role pilot\|eval\|safety\|train` | 골드의 `role` 로 거른다 (AI Hub 표본) |
| `--source real\|synthetic\|aihub` | 골드의 `source` 로 거른다. 섞여 있으면 경고한다 |
| `--per-emotion 버전` | 그 버전의 감정별 P/R/F1 을 함께 낸다 |

**Micro F1·Jaccard 는 challenge set 을 빼고 봐야 한다** (계획 §7.2·8.6). challenge set 은 희소 감정을
의도적으로 몰아넣은 세트라 실제 분포가 아니다. Macro F1·감정별 F1 은 두 세트를 합쳐서 본다.

출력은 표 네 개(+ 감정별)다: **감정**(세션 단위) · **강도** · **사건**(IoU 0.3/0.5/0.7 을 열로 나란히) ·
**층별**(아래 「층」). 버전 이름이 열 또는 행으로 붙는다.

## 파일럿 도구

```
        ┌─ 실사용자 DB ─┐
             psql
               ▼
        dump.py --anonymize --pseudonymize --sample 100
               │
               ├──▶ name-candidates.txt ──▶ 사람 검토 ──▶ names.txt ─┐
               │                                                      │ (2차 실행)
               ├──▶ conversations.txt ◀───────────────────────────────┘
               │          │
               │          ├──▶ labeler.html (A) ──▶ gold-A.json ─┐
               │          └──▶ labeler.html (B) ──▶ gold-B.json ─┴─▶ merge.py
               │                                                        │
               │                                        disagreements.md ┤ 조정
               │                                        gold-agreed.json ┘
               │
               └──▶ 프로브 러너 ──▶ pred-<변형>.json ──▶ score.py
```

### `dump.py` — DB 의 state_json 을 꺼내고 비식별화한다

DB 에 직접 붙지 않는다. 내보내기는 psql 이 하고 변환·비식별화만 맡는다.

```bash
psql "$DB_URL" -At -c \
  "SELECT state_json FROM retrospects WHERE status='COMPLETED' ORDER BY id" > sessions.jsonl
```

**실사용자 데이터는 두 번 돌린다.** 사람 이름은 자동으로 못 가리기 때문이다.

```bash
# 1차 — 표본을 정하고 이름 후보를 뽑는다
python3 dump.py --in sessions.jsonl --anonymize --pseudonymize \
  --sample 100 --seed 20260927 \
  --review-names data/name-candidates.txt --id-map data/id-map.json \
  --conversations data/conversations.txt

# name-candidates.txt 를 사람이 훑어 실제 이름만 남긴다 → names.txt

# 2차 — 검토된 이름까지 가린다
python3 dump.py --in sessions.jsonl --anonymize --pseudonymize \
  --sample 100 --seed 20260927 --names data/names.txt \
  --id-map data/id-map.json --conversations data/conversations.txt
```

| 옵션 | 뜻 |
|---|---|
| `--anonymize` | 전화·이메일·주민번호·계좌·카드·URL·아이디를 가린다. **실사용자 데이터엔 필수** |
| `--review-names` | 이름 후보와 빈도를 뽑는다. 자동 판별이 아니라 **사람이 검토할 입력**이다 |
| `--names` | 검토를 마친 이름을 `[사람N]` 으로 치환. 번호는 덤프 전체에서 일관된다 |
| `--pseudonymize` | 세션 ID 를 해시로. 라벨러가 원본 세션·사용자를 되짚지 못하게 |
| `--id-map` | 가명 → 원본 ID 매핑. **라벨 세트와 다른 곳에 보관한다** |
| `--sample N --seed S` | 표본 추출. 시드를 적어 두면 같은 표본을 다시 만들 수 있다 |
| `--source real\|synthetic` | 대화 헤더에 실린다. 실참여와 가상 대화를 섞어 집계하지 않기 위해(계획 §7.1) |

⚠ **자동 비식별화는 완전하지 않다.** 날짜·지명·직장명·드문 표현으로도 사람이 특정될 수 있다.
라벨링 전에 사람이 한 번 훑어보는 단계를 건너뛰지 말 것.

⚠ `--predictions` 로 나오는 운영 예측은 **구 택소노미(v1)** 다. 정본 골드와 같은 채점표에
올리지 않는다(`score.py` 가 거부한다). 대화는 감정 키를 담지 않으므로 택소노미와 무관하다 — **실사용 대화를 v2 로
라벨링해도 된다.**

### 프로브 러너 — 같은 대화에 변형을 갈아 끼운다

```bash
PROBE_IN=data/conversations.txt PROBE_OUT=/tmp/pred-comb.json \
PROBE_VARIANT=FEW_SHOT_COMBINED \
  ./gradlew cleanTest test --tests "*EmotionExtractionProbeRunner"
```

`cleanTest` 를 꼭 붙인다 — Gradle 은 환경변수를 입력으로 추적하지 않아 변형만 바꾸면 건너뛴다.
temperature 0 과 RPM 스로틀(4.5초)이 내장돼 있다.

### `labeler.html` — 골드를 다는 화면

브라우저에서 그냥 연다(파일 하나, 서버 불필요). **정본(v2) 기준**이다.

- 헤더에 **라벨러 ID**(A/B)를 먼저 넣는다. 내보내는 파일 이름이 `gold-A.json` 이 된다
- 대화를 `[U1]` `[U2]` 로 번호 붙여 보여주고, **발화를 눌러** 사건 배정·감정 근거·강도 근거를 찍는다
  (강도 근거는 「강도 근거 찍기」를 누른 뒤 — 파란 테두리)
- 사건마다 **명시적 표현 여부 · 판단 특성 · 라벨링 상태 · 판단 불가**를 찍는다
- 감정은 사건 **안에** 달린다. 대표 감정 12종 · 강도 **1·2·3·?(판단 어려움)** · 타인의 감정
- **판단 불가 3종을 구분**한다 — 감정 정보 부족(빈 목록이 정답, 채점 포함) / 대표 감정 판단
  어려움 / 분류 체계 밖(원문 기록). 뒤 둘은 채점에서 빠진다
- **12종 구분 기준표**를 화면에서 펼쳐 볼 수 있다. 강도 앵커는 상시 표시
- 불러올 때 **순서를 랜덤화**한다(감정별로 몰아서 라벨링하면 기준이 미끄러진다 — 계획 §8.8)
- 모델 출력을 보여주지 않는다(blind)
- 내보낼 때 **빠진 칸을 알려 준다**
- 작업은 localStorage 에 자동저장되지만 **수시로 「JSON 내보내기」** 를 눌러 파일로 남길 것

### `quick-labeler.html` — AI Hub 표본을 키보드로 빠르게

`aihub/sample.py` 가 뽑은 `data/sample-r1/*.jsonl` 전용이다. AI Hub 대화는 한 상황을 2~3턴으로 말하는
짧은 형식이라 **사건을 1개로 고정하고 사용자 발화 전부를 그 사건에 배정**한다. 사람은 감정·강도·근거
발화·판단 보류·명시 판단만 찍는다. 내보내는 골드는 `labeler.html` 과 같은 v2 라 `merge.py` 에 그대로 넣는다.

```bash
cd momentory-be/eval && python3 -m http.server 8765
# http://localhost:8765/quick-labeler.html  (다른 표본: ?sample=sample-r2)
```

- localhost 로 열면 `pilot`·`eval`·`safety`·`train` 네 세트를 자동으로 불러온다. 헤더에서 **라벨러 A/B** 와
  세트를 고르고, `assign` 에 그 라벨러가 들어 있는 항목만 보인다(파일럿·평가는 둘 다, 안전판·학습은 반씩)
- 순서는 라벨러·세트별로 랜덤이고, 판정은 라벨러별로 따로 저장된다
- 안전판의 애정·뿌듯함 10건은 표적 수집 판정(`prefill`)으로 **감정만** 미리 채운다. 강도·근거는 사람이 찍는다
- 감지기 힌트(`V`)는 `stratum`·`lex` 와 걸린 표현을 표시한다. AI Hub 원래 라벨(`proxy`·`aihub.minor`)은 보여주지 않는다
- **강도에 기본값이 없다.** 깜빡한 강도가 조용히 2로 들어가면 IAA 가 부풀려진다

| 키 | 하는 일 |
|---|---|
| `Q` `W` `E` `R` `T` `Y` `U` `I` `P` | 기쁨 평온 슬픔 불안 분노 실망 부끄러움 혼란 미안함 (`harvest.html` 과 같은 자리) |
| `A` `S` | 애정 · 뿌듯함 (숫자를 강도에 써서 옮겼다) |
| `B` | 지침 (2026-10-13 추가 — 남은 빈 자리) |
| `1` `2` `3` `?`(`/`) | 초점 감정의 강도. `?` 는 판단 어려움 |
| `J` `K` `L` | 초점 감정의 근거 발화 U1 U2 U3 켜고 끄기. 발화를 눌러도 된다 |
| `Tab` · `⌫` · `O` | 초점 이동 · 초점 감정 빼기 · 타인 감정 |
| `Z` `X` `C` | 판단 보류: 감정 정보 부족 / 대표 감정 판단 어려움 / 분류 체계 밖(원문 칸이 열린다) |
| `F` `G` `H` | 명시 판단: 있음 / 없음 / 판단 어려움 — 감지기와 따로 사람이 본다 |
| `D` · `M` · `N` | 경계 사례 · 의견 조정 필요 · 메모 |
| `Enter` · `←` `→` | 다음 · 이동 |

키는 물리 키(`e.code`)로 받아서 **한글 입력 상태여도 그대로 동작한다.**

harvest.html 의 교훈을 따랐다: 표본은 저장하지 않고 **판정만** localStorage 에 둔다(세트 지문이 바뀌어도
판정은 id 로 살린다). 「골드 내보내기」는 **지금 세트의 완료 항목만** `gold-<세트>-<라벨러>.json` 으로 낸다 —
강도를 안 찍은 감정이 들어가면 `merge.py` 가 엉뚱한 칸에 센다. 이어 하기는 그 골드 파일을 다시 불러오면
된다(형식은 전체 `JSON.parse` 로 판별, 끌어다 놓기 가능). 40건 넘게 안 내보내면 상단에 경고가 뜬다.

```bash
python3 merge.py --a data/gold-pilot-A.json --b data/gold-pilot-B.json \
  --report data/disagreements-pilot.md --merge data/gold-pilot-agreed.json
```

### `aihub/` — AI Hub 018.감성대화 활용

계획 §6.1. **이 코퍼스의 라벨은 쓰지 않는다.** 페르소나와 감정 코드를 주고 작성하게 만든
데이터라 라벨이 *지시된* 감정이고, 발화에 드러난 감정과 느슨하게 붙어 있다 — 실측으로
`기쁨|편안한` 3건 중 2건이 우리 기준으로는 기쁨이었다. 정본 §8.1("라벨의 근거는 사용자
발화에서 찾는다")과 기준이 다르다. 쓰는 것은 **텍스트**다.

| 파일 | 하는 일 |
|---|---|
| `mapping.json` | 소분류 60종 → 정본 12종 매핑표. direct / approx / 체계 밖. 지침에 대응하는 소분류는 없다 |
| `pick_double.py` | 평가셋에서 2인 독립 라벨링할 일부(기본 60건)를 내용이 겹치지 않게 고른다. `eval.jsonl` assign 과 `manifest.json` 의 `double` 을 고친다 |
| `convert.py` | 매핑 적용 + **커버리지 리포트**. 산출물보다 "무엇이 안 덮이는가"가 목적이다 |
| `harvest.py` | **애정·뿌듯함 후보 발화 수집.** 라벨이 아니라 표현을 긁는다 |
| `harvest.html` | 후보를 키보드로 빠르게 판정하는 화면. 이어서 하기 지원 |
| `migrate_reviewed.py` | id 규칙이 바뀌었을 때 예전 판정 파일을 맞춰 준다 |
| `sample.py` | **층화 추출** — 파일럿·평가·학습 라벨링 후보를 뽑는다(계획 §7.4) |
| `diversity.py` | **다양성 점검** — 감정 묶음별 근접 중복·상황 쏠림·단어 쏠림, 학습–평가 유출 |

> ⚠ **후보 id 에 split 이 들어간다.** AI Hub 의 talk-id 는 training 과 validation 사이에서
> 겹친다(실측 9건 — `Pro_05153_00002` 가 양쪽에 다른 내용으로 있다). split 을 안 붙이면 판정
> 화면에서 두 항목이 한 판정을 공유해 **하나가 검토되지 않은 채 값이 들어간다.**

⚠ **AI Hub 이용 조건은 [계획 §6.1.1](../docs/model-comparison-plan.md)에 정리했다** — 학습용으로만 쓴다,
출처를 표기한다, 제3자 제공과 국외 반출은 금지된다(해외 API·GPU 해석은 문의 중). 변환·수집 결과는
`eval/data/`(gitignore)에 두고 **매핑표와 스크립트만 커밋한다.**

#### 표적 수집 — 왜 전수 확정이 아닌가

`convert.py --report` 실측(58,268건): **애정 0건 · 뿌듯함 direct 0건.** 그런데 텍스트에는
표현이 있다 — 라벨 체계에 자리가 없어 슬픔·기쁨으로 흡수돼 있을 뿐이다.

approx 14,943건을 전수 확정하는 길은 막혀 있다. **소분류 단위로 접을 수가 없기 때문이다** —
`분노|안달하는` 표본 4건이 각각 분노·불안·불안·혼란이고, `당황|한심한`에는 "자식이 하나인
줄 알았는데 둘이 됐어"가 들어 있다. 개별로 가면 14,943건 × 30초 ≈ 125시간이다.

그래서 **비어 있는 두 감정만 표적으로 모은다.**

```bash
python3 aihub/harvest.py --dir "…/018.감성대화" --out data/harvest-candidates.jsonl
```

**재현율 우선**으로 넓게 긁고 정밀도는 사람이 만든다 — 놓친 것은 되찾을 수 없지만 잘못 긁은
것은 한 번 눌러 버리면 된다. 다만 **기계적으로 확실한 오탐은 보내지 않는다**: 「보고 싶어」
단독(「이야기해보고 싶어」를 긁는다) · 「든든한」(든든한 직장) · 「소중한」(소중한 시간)은 뺐다.

그다음 `aihub/harvest.html` 을 **브라우저에서 직접 연다**(파일을 더블클릭). 후보 파일을
불러오면:

- 매치된 표현을 **하이라이트**하고 앞뒤 대화를 함께 보여준다
- **키 하나 = 그 감정으로 정하고 다음으로.** 찾는 것 `1` 애정 · `2` 뿌듯함 · `3` 애정+뿌듯함,
  다른 감정 `q` 기쁨 `w` 평온 `e` 슬픔 `r` 불안 `t` 분노 `y` 실망 `u` 부끄러움 `i` 혼란 `p` 미안함 `b` 지침,
  그 외 `o` 체계 밖 · `4` 해당 없음 · `5` 애매
- **`Shift`+키는 넘어가지 않고 더한다** — 복합 감정("그녀가 더는 나를 사랑하지 않는대" =
  애정 + 슬픔). 한 번 더 누르면 뺀다. `Enter` 는 그냥 다음
- **애정·뿌듯함이 아닌 것도 버리지 않는다.** 후보로 걸린 이상 감정 표현이 들어 있는 문장이라
  어휘 사전의 재료다. `체계 밖`(고마움·미안함·죄책감·후회·질투)은 정본 §8.3 대로 억지로
  12종에 맞추지 않고 따로 모아 **감정 체계 개편 자료**로 쓴다
- `←` `→` 로 되돌아가 고칠 수 있다. 상단에 **건진 수**(애정·뿌듯함·다른 감정)가 실시간으로 뜬다
- **AI Hub 의 원래 라벨을 보여주지 않는다** — 발화만 보고 판단한다
- 순서를 랜덤화한다(축별로 몰아 보면 기준이 미끄러진다 — 계획 §8.8)
- localStorage 에 자동저장되지만 **수시로 「JSON 내보내기」** — 40건 넘게 안 내보내면 상단에
  빨간 경고가 뜬다. localStorage 는 브라우저 데이터를 지우면 함께 사라진다

> ⚠ **후보 목록은 localStorage 에 담지 않는다.** 2,243건이면 3.3MB 이고, 판정마다 동기적으로
> 통째를 다시 쓰면 **화면이 멈추고 용량 한도(보통 5MB)에 걸려 저장이 통째로 실패한다.**
> 파일에서 다시 만들 수 있는 것은 저장하지 않고 **판정만** 남긴다(전부 판정해도 150KB 안팎).
> 그래서 새로고침하면 **후보 파일을 다시 불러와야** 하고, 불러오면 저장돼 있던 판정을 자동으로
> 이어받는다 — 같은 후보 목록인지는 지문(개수 + 첫·끝 id)으로 확인한다.

#### 이어서 하기

같은 「후보 불러오기」 버튼이 두 형식을 다 받는다. **후보(.jsonl)를 먼저 불러온 뒤 판정
파일(.json)을 불러오면** 판정이 복원되고 **첫 미판정 항목으로 건너뛴다.**

들어간다. `decisions` 가 이어하기용이다.

`harvest.py` 의 id 규칙이 바뀌어 예전 판정 파일이 안 맞으면 `migrate_reviewed.py` 가 문장으로

python3 aihub/migrate_reviewed.py --reviewed ~/Downloads/harvest-reviewed.json \

문장이 여러 후보에 걸리면 **건너뛴다** — 잘못 붙이느니 다시 보는 편이 낫다.

내보낸 `harvest-reviewed.json` 은 `verdict`(토큰 배열)·`primary`·`byEmotion` 집계를 담는다.

1. **감정 어휘 사전** — V0 베이스라인과 §5.1 명시적 표현 감지기의 재료
2. **씨앗** — 자체 생성 세트에서 애정·뿌듯함 칸을 채울 출발 문장(§7.3)

### `merge.py` — 2인 독립 라벨을 합치고 불일치를 뽑는다

계획 §8.5 의 조정 절차를 실행 가능하게 만든 자리다.

```bash
python3 merge.py --a data/gold-A.json --b data/gold-B.json \
  --report data/disagreements.md --merge data/gold-agreed.json
```

내는 것:

1. **일치도(IAA)** — 계획 §8.9 의 상한선 좌표. 감정은 라벨별 이진 카파의 매크로 평균(다중
   라벨이라 단일 카파가 안 된다), 강도는 1·2·3 가중 카파, 보류('판단 어려움')는 따로 센다.
   **감정별 카파를 낮은 순으로** 내므로 기준 문서를 보강할 후보가 바로 보인다.
2. **불일치 목록** — 원인을 **사건 구분 / 대표 감정 / 강도 / 명시적 표현 / 판단 불가**로 분류한다.
   조정 회의에서 이 순서로 훑는다. 각 항목에 체크박스가 붙어 있다.
3. **합의 골드** — 두 라벨이 완전히 같은 세션만 담는다. 갈린 세션은 **자동으로 한쪽을 고르지
   않는다** — 사람이 조정한 뒤 직접 넣는다.

감정 일치는 **세션 단위**로 잰다(계획 §9.2). 사건 정렬 규칙의 자의성이 IAA 에 섞이면 "기준이
안 맞는 건지 정렬이 안 맞는 건지" 구분할 수 없다. 사건·명시적 표현처럼 사건에 매인 항목만
근거 발화 IoU 로 짝지어 비교한다.

## 데이터 계약

골드는 `labeler.html`·`quick-labeler.html` 이 내는 모양이다. 예측은 `sessionId`·`taxonomy`·`events`·`emotions` 만
같으면 된다(아래 「예측」).

```json
[
  {
    "sessionId": "p-16dc368a",
    "taxonomy": "v2",
    "labeler": "A",
    "source": "real",
    "set": "natural",
    "events": [
      {"id": 1, "label": "회의", "summary": "회의에서 내 의견이 빠짐",
       "evidence": [1, 2],
       "explicit": "yes", "status": "final",
       "traits": ["negation"], "undecidable": null}
    ],
    "emotions": [
      {"eventId": 1, "normalized": "disappointed", "intensity": 2,
       "evidenceIds": [2], "intensityEvidenceIds": [2]}
    ]
  }
]
```

| 필드 | 뜻 |
|---|---|
| `taxonomy` | `v2` = 정본 12종. 도구가 이 값으로 섞임을 막는다 |
| `source` | `real`(실참여) / `synthetic`(가상) / `aihub`(AI Hub 표본, `quick-labeler.html`). 섞어서 집계하지 않는다 |
| `role` · `stratum` · `lex` | AI Hub 표본만. 세트(pilot/eval/safety/train)와 감지기 판정 — 감지기 기준 명시(`stratum`)와 사람 기준 명시(`events[].explicit`)로 따로 잘라 채점한다 |
| `events[].evidence` | 그 사건에 속하는 **사용자 발화 번호 전체**. 사건 정렬의 기준 |
| `events[].explicit` | `yes` / `no` / `unsure` — 명시적 감정 표현 여부(계획 §5.2) |
| `events[].status` | `final` / `discuss` / `insufficient` — 라벨링 상태 |
| `events[].traits` | `negation` `correction` `quote` `other` `phase` `mixed` `boundary`(경계 사례 — 복합·경계 층 채점용) |
| `events[].undecidable` | `no_emotion_info`(빈 목록이 정답) / `emotion_unclear` / `out_of_scope` — 뒤 둘은 채점 제외 |
| `emotions[].normalized` | 정본 12종: `joy` `calm` `proud` `affection` `sad` `anxious` `angry` `disappointed` `ashamed` `confused` `sorry` `exhausted` |
| `emotions[].intensity` | `1` `2` `3`, 또는 판단 어려움이면 **`null`** |
| `emotions[].evidenceIds` | 그 감정의 근거 발화 번호. `evidence` 의 부분집합 |
| `emotions[].intensityEvidenceIds` | 강도 근거. 비우면 감정 근거와 같다고 본다 |
| `emotions[].experiencer` | `"other"` 면 타인 감정이라 자기 감정 채점에서 빠지고 오탐률의 분모가 된다 |

**시점(`phase`)은 정본에서 채점 대상이 아니다**(계획 §4.1). 사건 당시 감정이 기본이고,
시점 차이는 `traits: ["phase"]` 메모로만 남긴다. 예측에 `phase` 가 있어도 `score.py` 는 무시한다.

### 예측

`score.py` 가 보는 것은 이것뿐이다. 나머지 필드(`raw`·`evidence` 원문·`keywords`·`phase` 등)는 있어도 무시한다.

```json
[
  {"sessionId": "p-16dc368a", "taxonomy": "v2",
   "events":   [{"id": 1, "evidence": [1, 2]}],
   "emotions": [{"eventId": 1, "normalized": "disappointed", "intensity": 2}]}
]
```

- **모든 행에 `"taxonomy": "v2"` 가 있어야 한다.** 구 채점기는 이 필드가 없으면 v1 로 봤고, 지금도 같다 —
  그래서 거부한다. v1 의 `anxious`·`angry`·`proud`·`calm` 은 v2 와 키가 같아 키만으로는 섞임을 다 못 거른다.
  예측을 만드는 쪽(프로브 러너 등)이 붙여야 한다
- `normalized` 가 12종 밖이거나 `intensity` 가 `1`·`2`·`3`·`null` 밖이면 거부한다
- `normalized` 를 비운 감정(체계 밖 — 계획 §4.2)과 `experiencer: "other"` 는 채점에서 뺀다
- `events[].evidence` 가 비면 그 사건은 어떤 골드 사건과도 짝지어지지 않는다(FP — 계획 §4.1)

## 지표

### 감정 — 세션 단위, 사건 정렬과 무관 (계획 §9.2)

**대표 지표가 정렬 규칙의 자의성에 오염되지 않도록** 감정·강도는 사건을 무시하고 세션 단위로 잰다.

| 지표 | 뜻 |
|---|---|
| 감정 Macro F1 | **대표 지표.** 12종을 동등하게 — 희소 감정을 못 잡는 걸 잡아낸다 |
| 감정 Micro F1 | 전체 예측 성능. 자주 나오는 감정이 지배한다 |
| Jaccard | 정답 감정 집합과 예측 집합의 겹침(둘 다 비면 1) |
| 감정 집합 완전 일치율 | 세션의 감정 집합을 통째로 맞힌 비율. `merge.py` 의 '대표 감정' 불일치와 같은 기준 |
| 라벨 개수 오차 · Hamming Loss | 과다/과소 예측 |
| 빈 목록 정답 맞힘 | 감정 정보 부족(정답 = 빈 목록) 세션에서 예측도 비운 비율 |
| 과잉 보류 | 정답 감정이 있는데 예측이 빈 목록인 비율 |
| 타인→자기 오탐률 | 타인 감정을 사용자 감정으로 잡은 비율 |
| 감정별 P/R/F1 (`--per-emotion`) | 특정 감정을 과잉 제안하거나 누락하는지. 지원·예측 수를 함께 낸다 |

### 강도 — 1·2·3, `null` = 판단 어려움 (계획 §9.3)

골드와 예측이 **둘 다 고른 감정**마다 강도를 비교한다. `null` 은 등급이 아니라 보류라 따로 센다.

| 지표 | 뜻 |
|---|---|
| 정확 일치율 · MAE · 가중 카파(QWK, 1~3) | 둘 다 등급을 낸 쌍에서. QWK 는 `merge.py` 와 같은 함수 |
| 2단계 오차율 | 1↔3 으로 틀린 비율 |
| **응답 비율** | 골드가 등급을 매긴 감정 전부 중 예측이 그 감정을 고르고 등급까지 낸 비율. 감정을 놓친 것과 보류한 것이 다 깎인다 — **쉬운 사례만 골라 맞힌 정확도가 되지 않게 정확도와 함께 읽는다** |
| 판단 보류율 | 맞힌 감정 중 예측이 `null` 을 낸 비율 |
| 보류 적절성 | 예측이 `null` 을 낸 것 중 골드도 `null` 인 비율 |

### 사건 — 정렬 필요 (계획 §9.1)

근거 발화 집합(`events[].evidence`)의 **IoU** 로 짝짓는다. **임계값 이상인 쌍만 후보로 두고** 그중 IoU 합이
최대인 이분 매칭을 고른다(`merge.py` 와 같은 원칙). 짝 없는 예측은 FP, 짝 없는 정답은 FN 이다.

**임계값 0.3 / 0.5 / 0.7 을 한 표에 열로 나란히 낸다(기본 0.5).** 볼 것은 절대값이 아니라 **순위가
유지되는가**다. 임계값에 따라 버전 순위가 뒤집히면 사건 F1 만으로 버전을 고를 수 없다는 뜻이고, 그건
실패가 아니라 보고할 발견이다.

| 지표 | 뜻 |
|---|---|
| 사건 개수 정확도 | 정렬 없이 개수만 비교 |
| Event Detection F1 | 매칭/FP/FN 에서 |
| Turn Assignment Macro F1 | 각 발화가 올바른 사건에 배정됐나 |
| Event Attribution | 감정이 올바른 사건에 붙었나(매칭된 사건에 한해) |
| 사건별 감정 집합 일치율 | 짝지은 사건의 감정 목록을 통째로 맞혔나. 감정 정보 부족 사건은 빈 목록이 정답 |

### 층 (계획 §9.2 「명시적·간접 표현별 F1」)

세션 단위 감정·강도 지표를 **골드 속성으로 잘라** 다시 낸다. 예측이 무엇을 냈든 같은 세션은 같은 층에 든다.
**층은 서로 겹친다** — 예를 들어 감정 정보 부족 세션도 사람 명시 판단이 `no` 면 「간접 (사람)」에 든다.

| 층 | 가르는 기준 |
|---|---|
| 명시 / 간접 (감지기) | 골드의 `stratum` — 어휘 사전 감지기 판정. §5 분기가 실제로 보낼 경로 |
| 명시 / 간접 / 판단 어려움 (사람) | `events[].explicit` 이 `yes` / `no` / `unsure`. 사건이 여럿이면 하나라도 `yes` 면 명시 |
| 보류 (감정 정보 부족) | 골드 자기 감정이 빈 세션. 여기서 볼 값은 「빈목록맞힘」이다 |
| 복합 | `traits` 에 `mixed` |
| 경계 | `traits` 에 `boundary` |

층이 작으면 값이 크게 흔들린다 — `n` 과 함께 읽는다.

## 채점 규칙에서 정한 것

읽는 사람이 숫자를 오해하지 않도록 명시한다. 파일럿·평가셋에서 재검토 대상이다.

1. **같은 감정이 한 세션에 여러 번 나오면 가장 강한 것으로 접는다**(등급이 `null` 보다 우선). 강도를 한
   쌍씩 비교하려면 (세션, 감정) 하나에 값이 하나여야 한다. `merge.py` 의 IAA 도 같은 규칙이라 상한과 바로 비교된다.
2. **골드에도 예측에도 없는 감정은 Macro F1 평균에서 뺀다.** 그 라벨의 F1 은 0 이 아니라
   '정의되지 않음'이다. 넣으면 테스트 세트가 작을 때 값이 실제보다 훨씬 낮게 보인다.
   예측만 있고 골드에 없는 라벨은 남긴다(F1=0) — 없는 감정을 지어낸 것에 벌점이 가야 한다.
   표에 `채점한 감정 라벨 수` 를 함께 내니 그 값과 같이 읽을 것.
3. **대표 감정 판단 어려움·분류 체계 밖 사건이 있는 세션은 감정·강도 채점에서 통째로 뺀다**(계획 §8.3).
   사건 하나만 빼려면 예측 감정이 그 사건 것인지 가려야 하고, 그러면 세션 단위 지표가 사건 정렬에 묶인다.
   AI Hub 표본은 사건이 1개라 같은 결과다. 뺀 수는 첫 줄에 나온다. 사건 지표에는 그대로 들어간다.
   **감정 정보 부족은 빼지 않는다** — 빈 목록이 정답이고, 예측 감정은 전부 FP 다.
4. **분모를 함께 낸다.** `비교 쌍`·`평가 대상`·`귀속 판정 수`·층의 `n` 이 작으면 그 지표는 못 믿는다.
5. **근거가 빈 사건은 짝짓지 않는다**(IoU 0). `merge.py` 는 사람끼리 비교라 둘 다 비면 1 로 본다.

## 자동 채점하지 않는 것

- **Event Summary Score** — BERTScore(별도 모델)와 사람 평가가 필요하다. 문서가 ROUGE 대신
  BERTScore 를 쓰라고 한 이유는 표현이 달라도 의미가 같을 수 있어서다.
- **근거 적합률** — 제시한 발화가 그 감정을 뒷받침하는지는 사람이 본다(계획 §9.2).
- **감정 간 혼동표** — 다중 라벨이라 정의를 먼저 정해야 한다(계획 §9.2). 아직 없다.
- **신뢰도(ECE·Brier·Coverage)** — 확률 출력이 필요한데 V1 은 내지 않는다. V2 부터 대상이다.
- **5줄 일기 평가** — 감정 모델과 분리해서 평가한다(계획 §7).

## 평가할 때 temperature

**0 으로 내리고 돌린다.** 운영은 0.7 을 유지하고(일기 문장이 딱딱해지지 않게), 평가에서만 내린다 —
0.7 이면 같은 입력에 결과가 흔들려 버전 간 차이인지 노이즈인지 구분할 수 없다.

```bash
SPRING_PROFILES_ACTIVE=local,eval ./gradlew bootRun
```

`application-eval.yml` 오버레이가 `temperature: 0` 과 프롬프트 변형 스윕용
`EMOTION_PROMPT_VARIANT` 를 걸어 준다.
