# 모델 비교 실험 계획 (권위본)

> 출처: `momentory docs/모델 비교.pdf`. 이 문서는 그 스펙을 **현재 코드 상태**와 **확정 결정**에 맞춰
> 다시 쓴 것이다. 충돌 시 이 문서가 우선한다.
> 관련: [`retro-chat-v2-plan.md`](retro-chat-v2-plan.md) — v2 대화 엔진 정본.
> 작성 2026-09-02.

## 0. TL;DR

현재 코드는 원본 문서의 **V1(LLM 프롬프트 모델)에 해당한다.** 다만 V1 프롬프트 스펙의 **절반만**
구현돼 있고(강도·시점·근거 번호 없음), 비교 실험을 돌릴 인프라는 **전무**하다.

이 계획은 ⑴ V1을 스펙대로 완성하고, ⑵ 자체 생성 테스트 세트를 만들고, ⑶ V0·V1·V2를 동일 세트에서
비교하는 순서로 간다. **감정 흐름 유형 판단은 범위에서 제외**했고, 그에 따라 원본 V4(사건 기반 감정
상태 전이 모델)도 드롭한다.

## 1. 확정된 결정

1. **감정 흐름 유형(flow type)은 만들지 않는다.** 원본 문서의 Flow Type Macro F1 · Transition Macro F1 ·
   State Sequence Accuracy 지표와 A6 ablation은 전부 삭제. 그 자리는 **시점(phase) Macro F1** 이 대신한다.
2. **버전 로드맵은 V0 → V1 → V2 → V3 네 단계.** 원본 V4는 존재 이유의 대부분이 흐름 유형이었고, 남는
   "시점별 감정 상태 예측"은 V3 멀티태스크의 phase 헤드로 흡수된다.
3. **V0 규칙 베이스라인은 필수다.** 라벨러가 1명이라 IAA(평가자 간 일치도) 상한선을 못 잰다. 기준을
   잡을 좌표가 하한선 하나뿐이므로 V0 없이는 V1 숫자를 해석할 수 없다.
4. **테스트 세트는 자체 생성한다.** 실사용 세션이 아직 거의 없다. 결과는 **상대 비교용**이며 절대 성능
   추정치가 아니다 — 보고 시 반드시 명시한다.
5. **라벨러 1명.** IAA 대신 intra-annotator(재라벨링) 일치도를 보고하고, 개인 편향 미통제를 limitation
   으로 명시한다.
6. **출력 스키마 확정이 라벨링보다 먼저다.** 라벨 스키마는 V1 출력 스키마와 1:1이어야 채점된다.
   프롬프트 *변형* 선택(zero-shot/few-shot/2단계)만 테스트 세트 이후로 미룬다.

## 2. 현재 상태 진단

### 2.1 V1에 해당하는 근거

| 항목 | 현황 |
|---|---|
| 모델 | Gemini `gemini-flash-lite-latest`, temperature 0.7 (`application.yml`) |
| 호출 | 일기 채팅 종료 시 **대화 전체로 1회**(G1) — `RetrospectEngine#generateDiary` |
| 출력 | `generationConfig.responseSchema` 구조화 JSON — `GeminiResponseSchemas` |
| 감정 | 고정 10종, 원본 문서 목록과 **정확히 일치** — `Emotion` |
| 교체 이음매 | `EmotionExtractor` 포트로 분리 완료 (V2 교체 지점) |

자체 학습 모델·규칙 모델은 없다. 감정 판단 경로는 LLM 하나뿐이다.

### 2.2 V1 스펙 대비 빠진 것

- **감정 강도 0~4** — 프롬프트·스키마 모두 없음. (구 v1 스크립트의 `after_intensity` 측정 스텝은 v2에서
  폐기되어 미사용.)
- **시점(전/중/직후/현재)** — `ExtractedEmotion.timing` 필드와 스키마 항목은 **있으나 프롬프트가 요청하지
  않아** 사실상 항상 null. `cause` 도 동일.
- **근거 발화 "번호"** — `evidence` 가 문장 원문이라 Turn Assignment 계열 지표를 채점할 수 없다.
- **「AI 발화를 사용자 감정의 근거로 쓰지 않는다」 지시 없음** — 히스토리에 `바바:` 발화가 그대로 들어간다.
- **사건 ≤2 제한이 감정 추출 경로에 없음** — 토픽 추출(G5)에만 있다.

### 2.3 구조적 결함 (평가 이전에 고쳐야 함)

1. ~~G1(감정)과 G5(토픽)가 같은 대화를 서로 모른 채 두 번 판단한다~~ → **해결: §3.4 대로 G1 하나로
   통합.** 토픽은 추출 결과에서 LLM 없이 파생시킨다.
2. **히스토리를 앞에서 자른다** (`history-char-budget: 1200`). 사건은 거의 항상 1~2턴에 나오므로 사건
   도입부가 먼저 날아간다.
3. **선택지 줄이 히스토리에 저장된다** — `addAssistantMessage(text + "\n" + optionLines(options))`.
   감정 추출에는 순수 노이즈인데 예산을 갉아먹는다.
4. **`TurnRequest.content` 에 길이 제한이 없다.** 6턴 상한이 무의미해질 수 있다.
5. **`confirmedEmotions` 를 골드 라벨로 쓸 수 없다.** 후보가 LLM 추출 감정 4개로 제한되고
   (`distinctNormalized(...).limit(4)`), 선택도 `limit1` 로 1개만 저장된다.

## 3. V1 재설계

### 3.1 출력 스키마

감정을 사건에 묶는다(현재는 사건과 무관한 평평한 리스트).

```json
{
  "events": [
    { "id": 1, "summary": "발표에서 말이 막힘", "evidence": [1, 2] }
  ],
  "emotions": [
    { "eventId": 1, "raw": "너무 불안했어요", "normalized": "anxious",
      "intensity": 3, "phase": "before",
      "evidence": "준비가 부족한 것 같아서 너무 불안했어요", "evidenceIds": [2] }
  ]
}
```

- `events` 최대 2개. `phase` 는 `before|during|after|now`. `intensity` 0~4.
- **`evidence` 는 사용자 발화 번호 배열이며, 두 곳의 뜻이 다르다** (§7.1 사건 정렬의 전제):
  - `events[].evidence` — 그 사건에 **속하는 사용자 발화 전체**(배정). **required.**
    사건 정렬 기준이자 Turn Assignment F1의 채점 대상이다. 근거 없이 뽑은 사건은 매칭에 실패해
    FP로 잡히는데, 이는 환각 사건에 대한 **의도된 페널티**다.
  - `emotions[].evidence` — 근거가 된 사용자 **문장 원문**. `emotions[].evidenceIds` — 그 문장의
    **발화 번호**(보통 1~2개), `events[].evidence` 의 부분집합.
  - 하나로 뭉뚱그리면 정렬이 불안정해진다. 사건은 넓게(배정), 감정은 좁게(근거).
  - 감정에 원문과 번호를 <b>둘 다</b> 두는 이유: 번호가 있어야 채점에서 근거를 기계적으로 대조하고,
    원문이 있어야 라벨링·일기 검증(Unsupported emotion rate)에서 사람이 바로 읽는다. 기존
    스냅샷의 `evidence`(문자열)와 타입이 그대로라 진행 중이던 세션도 깨지지 않는다.
- 감정이 없으면 `emotions: []` — 억지로 채우지 않는다(테스트 세트에 "감정 없음" 영역이 있다).
- **타인 감정**: V1은 사용자 감정만 출력한다. 테스트 세트에 타인 감정 케이스를 넣어 **오탐률**로 측정한다
  (원본 문서 종합점수의 "감정 주체 F1" 자리).
- 흐름 유형 필드는 두지 않는다.

### 3.2 프롬프트에 추가할 규칙

원본 문서에 있는데 현재 빠진 것들:

- 「AI(바바)의 발화를 사용자 감정의 근거로 사용하지 않는다」
- 「사용자가 명시하지 않은 감정은 추측하지 않는다」 (현재 "지어내지 말라"보다 강하게)
- 「근거는 반드시 `[U번호]` 로 지목한다」

### 3.3 히스토리 처리

**비용은 자르는 이유가 못 된다.** 대화가 6턴으로 상한이 박혀 있어 히스토리가 무한정 자라지 않는다.
세션 끝 기준 전문 약 2,000자 ≈ 2,000토큰(추정). 히스토리를 싣는 콜은 세션당 9번(G2×6 + G1·G4·G5)이고,
전문 대비 1200자 컷의 차이는 **약 2,000토큰 = 세션당 0.0002 USD**(`application.yml` 요율 기준). 세션 전체가
0.002 USD 수준이므로 자르기는 그 10%를 아끼면서 사건 도입부를 버리고 있다.

예산의 목적을 **"비용 절감"이 아니라 "폭주 방지"** 로 바꾼다.

| 콜 | 빈도 | 히스토리 정책 |
|---|---|---|
| G2 일기 턴 | 세션당 6회 | 예산 적용 — 최근 3턴 전문 + 그 앞은 슬롯 요약으로 대체 |
| **G1 감정 · G4 일기 · G5 토픽** | **각 1회** | **전문 무삭제** |

추가로:

1. **프롬프트 조립 시 선택지 줄 제거** — 저장은 그대로, 프롬프트에만 안 넣는다(20~30% 절감, 무손실).
2. **사용자 발화에만 번호 부여** — AI 질문은 지시 대상 해소용으로 남기되 번호를 주지 않아 근거로 지목할
   수 없게 한다. 페이로드 감소 + 근거 번호 구현 + AI 발화 오염 차단이 한 번에 해결된다.

   ```
   [U1] 오늘 발표에서 말이 막혔어요
   (바바) 그때 어떤 기분이었어요?
   [U2] 준비가 부족한 것 같아서 너무 불안했어요
   ```
3. 자를 때는 **앞이 아니라 중간**을 자른다.
4. `TurnRequest.content` 에 발화 단위 상한(`@Size(max = 1000)` 수준)을 건다.

### 3.4 G1/G5 통합 (구현 완료)

G1이 사건·감정·**키워드**를 한 콜로 뽑고, 토픽은 그 결과에서 **LLM 없이 파생**시킨다. 같은 대화에 대한
감정 판단이 한 곳에서만 일어나야 채점이 성립한다.

**추출 출력에 키워드가 붙는다** — 키워드는 사건이 아니라 누적·집계의 단위라 사건에서 파생시킬 수 없다.
G5 를 없애려면 G1 이 함께 뽑아야 한다.

```json
"keywords": [ { "label": "발표", "eventId": 1 } ]
```

**사건에 짧은 `label` 을 추가했다.** `retrospect_topics.label` 은 누적 집계의 키(`idx_rt_user_label`)라
날마다 같은 일이 같은 이름으로 쌓여야 한다. 사건 요약은 문장이라 그대로 쓰면 집계가 깨진다 —
`label`(짧은 이름, 토픽용)과 `summary`(한 줄 요약, Event Summary Score 채점용)를 나눈다. `label` 이
비면 `summary` 로 대신한다.

**감정 물려주기 규칙** (토픽 파생, LLM 호출 없음):

| 토픽 | 감정 |
|---|---|
| 사건(SCHEDULE) | `eventId` 가 그 사건인 감정 |
| 사건이 **하나뿐**일 때 | 위 + `eventId` 가 비어 있는 감정도 그 사건 것으로 본다 |
| 사건이 둘일 때 | 안 붙은 감정은 **어느 쪽에도 붙이지 않는다**(잘못 귀속시키느니 비운다) |
| 키워드(KEYWORD) | 매인 사건의 감정. 매인 사건이 없으면 세션 전체 감정 |

**삭제한 것**: `TopicExtractor` 포트 · `GeminiTopicExtractor` · `ExtractedTopic` · `topicExtractPrompt`
· 토픽 응답 스키마 · `LlmRole.G5`.

⚠ **계측 축이 바뀐다** — `llm-usage` 로그에 `AI-G5` 가 더 이상 나오지 않는다. 역할별 비용 집계를
쓰는 로그 파이프라인이 있다면 함께 조정해야 한다. 세션당 LLM 콜이 1회 줄어드는 효과도 있다.

### 3.5 프롬프트 변형 스위치

원본 문서의 비교 실험 5종을 돌리려면 프롬프트를 갈아끼울 축이 필요하다. `EmotionExtractor` 포트 아래에
변형만 enum으로 둔다: `ZERO_SHOT` / `FEW_SHOT` / `FEW_SHOT_BOUNDARY`(화남·답답·막막 경계) / `TWO_STAGE`
(근거 발화 선별 → 감정 판단).

**평가 시 temperature 는 반드시 0.** 0.7이면 같은 입력에 결과가 흔들려 버전 간 차이인지 노이즈인지
구분할 수 없다.

### 4.1 AI Hub 감성대화 말뭉치 (`018.감성대화`)

**V1 평가 정답지로는 쓸 수 없다. V2 워밍업 자산으로는 유효하다.**

규모: 학습 51,628건 + 검증 6,640건, 2~3턴, 사람 발화 평균 95자, 60종(6대분류 × 10소분류) 균등.

택소노미가 Momentory 10종의 절반만 덮는다:

| Momentory | AI Hub 소분류 | 판정 |
|---|---|---|
| 불안 | 불안, 걱정스러운, 두려운, 초조한, 스트레스 받는 | 충분 |
| 우울 | 우울한, 낙담한, 슬픔, 실망한, 눈물이 나는 | 충분 |
| 화남 | 분노, 노여워하는, 짜증내는, 성가신, 툴툴대는 | 충분 |
| 행복 | 기쁨, 신이 난, 만족스러운, 감사하는 | 충분 |
| 평온 | 느긋, 편안한, 안도 | 충분 |
| 답답 | 좌절한, 안달하는 (근사) | 불충분 |
| 막막 | 회의적인·염세적인이 멀게 걸침 | 사실상 없음 |
| 무기력 | 마비된 정도 | 사실상 없음 |
| 뿌듯 | 자신하는 정도 | 사실상 없음 |
| 피곤 | — | **완전 부재** |

- 못 덮는 쪽에 **답답·막막**이 있다. 원본 문서가 challenge set으로 지목한 바로 그 경계 감정이고, 이
  데이터로 학습하면 답답이 화남으로 흡수되는 편향이 생길 수 있다.
- 역방향도 문제다. AI Hub의 **상처**(배신당한·억울한·질투하는), **당황**(부끄러운·죄책감의·열등감),
  고립된·외로운은 Momentory 10종에 갈 자리가 없어 강제 매핑하면 노이즈가 된다.
- 구조 불일치: **단일 라벨**(대화 1건 = 감정 1개)이라 Jaccard·다중라벨 Macro F1 채점 불가. 강도·시점·
  사건·근거 전부 없음.
- 도메인 불일치: 상황이 대인관계·건강/죽음·학교폭력/따돌림·재정 중심, 연령은 노년 31%. 피곤·평온 같은
  일상 감정이 없는 이유다.

⚠ **AI Hub 이용 약관을 확인한 뒤 사용한다** — 2차 저작물·연구 외 활용에 제약이 있을 수 있다.

## 5. 평가 데이터 설계

### 5.1 구성

**화자 3명 확보(사용자 포함, 2026-09-02).** 라벨러는 1명이지만 화자가 여럿이라 두 편향 중
데이터 편향은 실질적으로 깨진다. 남는 limitation 은 1인 라벨 하나다.

| 세트 | 규모 | 만드는 법 | 라벨 |
|---|---|---|---|
| 자연 세트 | **45세션** (3명 × 15) | **실제 앱으로** 대화. 감정을 미리 정하지 않음 | blind, 약 4h |
| Challenge set | **60~80세션** | **정답을 먼저 정하고 생성**(by-construction) | 검수만, 약 2h |
| 재라벨 | 자연 세트 중 20 | 최소 1주 간격 재라벨링 | 자기 일치도, 약 1.5h |

Challenge 를 50 → 60~80 으로 키운 이유: 자연 45세션이면 감정 인스턴스가 약 110개인데 자연 분포라
불안·우울·답답에 쏠리고 **평온·뿌듯·무기력·피곤은 각 3~5개**밖에 안 나온다. 희소 감정을 challenge 가
짊어져야 감정당 6~8개가 된다. 그래도 최소 기준(30)에는 못 미치므로 **희소 감정 F1 은 참고치이지
결론의 근거가 아니라고 보고한다** — 채점기가 감정별 `지원` 수를 함께 내니 그 값과 같이 읽는다.

### 5.1.1 대화는 앱에서, 예측은 따로 (중요)

**대화(입력)와 예측(출력)을 분리한다.**

- **대화는 실제 앱으로 받는다** — AI 질문이 진짜라 대화 모양이 프로덕션과 같고(문서에 손으로 쓰면 AI 턴이
  가짜라 입력 분포가 어긋난다), `state_json` 에 남아 덤프가 공짜다. 하루 1회 제한은 `userId` 기준이라
  계정을 나누면 걸리지 않는다.
- **예측은 나중에 temperature 0 으로 재실행한다** — 앱은 운영 설정(0.7)이라 그대로 쓰면 평가 조건이
  깨진다. 분리해두면 같은 대화에 프롬프트 변형(zero-shot/few-shot/2단계)을 여러 번 돌려 비교할 수 있다.

**V1은 학습이 없으므로 train/valid 분할이 필요 없다.** 원본 문서의 70/15/15는 V2 진입 시점에 적용한다.

Challenge set이 by-construction이라 라벨링 비용이 세션당 1~2분으로 떨어진다. 총 작업량 **10~13시간**.

Challenge set 커버 영역: 화남/답답/막막 경계, 타인 감정, 간접 표현, 부정 표현("화난 건 아니고 답답했어"),
감정 없음, 복수 사건, 애매한 시간.

### 5.2 희소 감정 — 두 세트의 지표를 분리한다

자연 분포로 뽑으면 불안·우울·답답에 쏠리고 평온·뿌듯·무기력·피곤은 몇 건 안 나와 Macro F1을 못 잰다.
희소 감정은 **challenge set이 채우는 구조**로 가되, 분포가 달라지므로 지표를 나눠 본다.

- **자연 세트만** → Micro F1, Jaccard (실제 분포에서의 성능)
- **두 세트 합산** → Macro F1, 감정별 P/R/F1 (희소 감정 처리 능력)

### 5.3 자체 생성의 한계와 완화

편향이 둘 겹친다: **라벨러 1인** + **데이터 자체 생성**.

- **라벨 편향은 못 깬다** — limitation으로 명시.
- **데이터 편향은 깰 수 있고, 비용 대비 효과가 가장 크다** → **지인 5~10명에게 각 8~10세션 부탁**.
  라벨러는 1명이어도 화자는 여럿이 된다. 비공개 테스트 기간이라 연구 목적 사전 동의를 받기 좋다.
- 화자 확보가 어려우면 **씨앗 하이브리드**: AI Hub의 실제 사람 발화 1문장을 씨앗으로 삼아 말투를 유지한
  채 6턴 회고로 확장. 순수 LLM 합성은 자연 세트에 쓰지 않는다(생성·평가를 같은 Gemini로 하면 순환이
  가장 심하다).
- 하루 1회 제한은 병목이 아니다 — `requireNoDiaryToday` 가 userId 기준이라 로컬 mock 로그인으로 계정을
  나누면 된다.

혼자 쓸 때 순환을 줄이는 장치:

1. **감정을 미리 정하지 않고 작성**(자연 세트 한정) — 라벨이 대화에서 나오게 한다.
2. **작성과 라벨링 사이 최소 1주** — 의도했던 감정의 기억을 흐린다.
3. **소재 매트릭스를 먼저 작성** — `상황 키워드 × 목표 감정` 표로 배분. 평온·피곤·뿌듯 칸을 의도적으로 채운다.

## 6. 라벨링 절차

### 6.1 스키마

§3.1 출력 스키마와 1:1. 가이드라인에 못 박을 것:

- **강도 0~4 앵커** — 사람 간·시점 간 편차가 가장 큰 항목. `0=감정 언급 없음, 1=살짝, 2=보통, 3=강함,
  4=압도적` 에 각각 실제 예문을 붙인다. QWK로 측정.
- **화남/답답/막막 경계 규칙** — 원본 문서 challenge 예시를 판정 규칙으로 승격.
- **"감정 없음" vs "판단 불가" 구분** — 전자는 정답(빈 배열), 후자는 채점 제외. 섞이면 지표가 오염된다.

### 6.2 pre-annotation 정책

- **자연 세트: blind 금지 해제 없음.** 라벨러가 1명이라 교차 검증이 없어 앵커링 위험이 2인일 때보다 크다.
- **Challenge set: by-construction 라벨 + 사람 검수.** 생성 결과가 의도와 어긋나는 경우가 반드시 나오므로
  검수를 건너뛰지 않는다. Challenge set으로 **Macro F1 절대값을 주장하지 않는다**(경계 사례 성능만 보고).
- 시간은 pre-annotation이 아니라 **도구**로 줄인다 — 대화를 `[U1]`,`[U2]` 로 번호 붙여 렌더하고
  감정/강도/시점/근거를 클릭으로 찍어 JSON을 뽑는 단일 HTML 페이지. 세션당 5~8분 → 3~5분.

### 6.3 드리프트 방지 (1인 라벨링의 최대 리스크)

며칠에 나눠 하면 1일차와 4일차 기준이 달라진다.

1. **순서 랜덤화** — 감정별로 몰아서 라벨링하지 않는다.
2. **배치 시작마다 앵커 예문 재확인.**
3. **마지막 일관성 패스** — 전체를 감정별로 재정렬해 훑는다. 이 패스에서 바꾼 라벨 수가 곧 드리프트 지표다.

### 6.4 기준 설정 (IAA 부재 시)

```
V0 (하한)  <  목표 기준  <  자기 일치도 (상한)
```

자기 일치도는 강도 QWK · 감정 집합 Krippendorff's alpha 로 측정한다. 원본 문서의 "임의로 0.8처럼 정하지
말라"를 1인 버전으로 지킨 것이다.

⚠ 자기 일치도가 잡는 것은 "스키마를 일관되게 적용할 수 있는가"뿐이다. **본인 특유의 체계적 편향은
못 잡는다**(일관되게 틀리면 일치도는 오히려 높다).

## 7. 평가 지표

원본 문서에서 **흐름 관련 3종(Transition Macro F1 · Flow Type Macro F1 · State Sequence Accuracy)을
삭제**하고 시점 지표를 넣었다.

**사건**
- Event Count Accuracy · Event Detection F1
- Turn Assignment Macro F1 (근거 발화 번호로 채점)
- Event Summary Score — BERTScore + 사람 평가 (ROUGE 부적합)

**감정 (다중 라벨) — 두 수준에서 따로 채점한다**

`emotions[].eventId` 때문에 감정 채점이 사건 정렬에 얹히면, 점수가 나빴을 때 감정 판단이 나쁜 건지
정렬이 나쁜 건지 구분할 수 없다. 문서의 대표 지표가 정렬 규칙의 자의성에 오염되면 안 되므로 분리한다.

- **세션 단위 (사건 무시) — 주 지표.** 세션 전체 감정 집합 vs 정답 감정 집합. **사건 정렬과 완전 독립.**
  - 대표: **Macro F1** / 보조: Micro F1, Jaccard
  - 감정별 P·R·F1, 감정 간 동시 혼동표 + 감정별 이진 혼동행렬, 라벨 개수 오차, Hamming Loss
  - **강도**(MAE, QWK)와 **시점**(Phase Macro F1)의 주 지표도 여기서 낸다.
- **사건 단위 (정렬 후) — 보조 지표.** **Event Attribution Accuracy**: 정렬에 성공한 사건 쌍에 한해,
  감정이 올바른 사건에 붙었는가.

이렇게 두면 정렬 규칙이 바뀌어도 대표 지표는 그대로고, 정렬 품질은 자기 지표로 따로 보인다.

**주체** — 타인 감정을 사용자 감정으로 잡은 **오탐률**

**신뢰도** — ECE, Brier Score, Coverage × Selective Accuracy (판단 보류 효과)

**5줄 일기 (감정 모델과 분리 평가)**
- 자동: BERTScore, Entity/Fact Consistency, Source coverage, Unsupported claim rate
- 사람: 충실도·순서·관점·자연스러움 1~5점
- **최우선: Unsupported emotion rate** — 근거 없는 감정을 일기에 추가한 비율

**운영** — 평균 응답시간, 세션당 토큰·비용

### 7.1 사건 정렬 규칙 (확정)

예측 사건과 정답 사건을 짝지어야 Event Detection F1 · Turn Assignment · Event Summary ·
Event Attribution 을 채점할 수 있다. (세션 단위 감정 지표는 §7 대로 정렬과 무관하다.)

**기준: `events[].evidence` 발화 번호 집합의 Jaccard(IoU).**

요약 의미 유사도(BERTScore·임베딩) 대신 근거 겹침을 쓰는 이유:

| | 근거 발화 IoU | 요약 의미 유사도 |
|---|---|---|
| 재현성 | 결정적 — 집합 연산 | 임베딩 모델 버전에 따라 점수가 변함 |
| 자의성 | 임계값 하나 | 임계값 + 모델 선택 |
| 설명력 | "발화 2,3이 겹쳐서 같은 사건" | "유사도 0.81이라서" |
| 표현 차이 | 요약이 달라도 근거가 같으면 매칭 | 강함 |
| 근거 오류 | 근거를 잘못 달면 실패 | 영향 없음 |

**채점이 또 다른 모델에 의존하기 시작하면**, 나중에 "V2가 V1보다 낫다"는 결론이 임베딩 모델 탓인지
해명해야 한다. 채점은 결정적일수록 좋다.

**알고리즘**

1. 사건이 최대 2개이므로 **전수 탐색으로 IoU 합이 최대인 이분 매칭**을 찾는다(경우의 수 2가지 —
   헝가리안 알고리즘 불필요).
2. **IoU 임계값 미만인 쌍은 매칭하지 않는다.** 짝 없는 예측 = FP(환각 사건), 짝 없는 정답 = FN(누락)
   → Event Detection F1.
3. **Event Count Accuracy 는 정렬 없이** 개수만 비교한다.

**임계값**: 기본 **0.5**. 자의적일 수밖에 없으므로 파일럿에서 **0.3 / 0.5 / 0.7 민감도를 함께 보고**한다.
확인할 것은 절대값이 아니라 **임계값을 바꿔도 버전 순위가 뒤집히지 않는가**이며, 뒤집히면 그 자체가
보고할 발견이다.

**요약 유사도 보조 매칭은 지금 넣지 않는다.** 파일럿에서 "근거는 안 겹치는데 명백히 같은 사건"이 몇 건
나오는지 세고, 유의미하게 많을 때만 추가한다(복잡도 증가 + 재현성 하락이 대가).

**라벨링 파급**: 정답에도 `events[].evidence` 가 필요하므로, 라벨러가 사용자 발화 각각을
`사건 1 / 사건 2 / 배경·기타` 로 배정한다. 세션당 약 30초 추가 — Turn Assignment F1 채점에 어차피
필요한 작업이라 순수 추가 비용은 아니다.

### 7.2 종합점수

개발 단계에서는 **합치지 않는다.** 버전 × 지표 성능표를 유지한다.

배포 모델을 하나 골라야 할 때만 적용(원본의 Flow 25% 제거 후 재배분):

| 지표 | 가중 |
|---|---|
| 감정 Macro F1 | 40% |
| 사건 F1 | 20% |
| Jaccard | 15% |
| 시점 Macro F1 | 15% |
| 주체 오탐 | 10% |

MAE·ECE처럼 낮을수록 좋은 값은 정규화 후 반영. 다만 **종합점수보다 "최소 조건 통과 모델 중 비용·속도
최선"** 선택을 권한다.

## 9. 작업 순서

1. **V1 출력 스키마 + 프롬프트(zero-shot) 구현** — §3.1~3.4. 변형 스위치는 자리만 만들고 zero-shot 하나만
   채운다. *라벨링보다 반드시 먼저* (라벨 스키마를 결정하므로).
   → **완료** (브랜치 `feat/emotion-extraction-v1`). §3.1~3.4 전부. `./gradlew clean check` 통과
   (408 테스트, 실패 0, 스킵 2 — 실제 API 키가 필요한 조건부 테스트).
2. **파일럿 10~15세션을 끝까지 한 바퀴** — 대화 생성 → 라벨링 → V1 실행 → **채점 스크립트 실행까지**.
   숫자가 나오는 데까지 간다.
3. **파일럿 결과로 스키마·가이드라인 수정.**
4. **본 데이터 생성 + 라벨링** (§5, §6).
5. **V0 베이스라인 구현.**

## 11. AGENTS.md 준수 (구현 시)

구현 착수 전 `momentory-be/AGENTS.md` 를 다시 확인한다. 이 계획에 특히 걸리는 조항:

- **API 계약 변경은 승인 필요** — §3.1 스키마 변경은 내부(LLM 어댑터) 계약이라 HTTP 계약에 영향이 없어야
  한다. `ExtractedEmotion` 확장이 `ReplyDto`·일기/토픽 응답에 새 필드를 노출하지 않는지 확인한다.
  `TurnRequest.content` 에 `@Size` 를 거는 것은 **요청 검증 강화 = 계약 변경**이므로 별도 승인 대상이다.
- **인터페이스 최소화** — 프롬프트 변형은 `EmotionExtractor` 구현체를 늘리지 말고 **enum + PromptFactory
  분기**로 처리한다. 전략·팩토리 남발 금지.
- **Flyway** — 감정 스키마 확장은 `state_json` 안이라 마이그레이션 불필요. `ExtractedEmotion` 필드 추가는
  **기존 스냅샷과의 역직렬화 호환**을 확인한다. 실측 결과(Jackson 3): **모르는 필드는 조용히 무시**되지만
  (`timing`·`cause` 제거는 안전) **빠진 primitive 는 실패**한다(`Cannot map null into type int`).
  → 스냅샷에 새 필드를 넣을 때는 **참조 타입(List·Integer)** 으로 두어야 구버전이 열린다. `events`(List)와
  `intensity`(Integer)를 그렇게 잡았다. `RetrospectStateCodecTest#deserializesPreEventSnapshot` 이 회귀를 막는다.
- **OpenAPI** — 응답 DTO가 바뀌면 계약 테스트와 `/v3/api-docs` 를 함께 갱신·검증.
- **테스트** — 새 스키마 파싱, 근거 번호 매핑, 히스토리 조립(선택지 제거·번호 부여)에 단위 테스트를 추가한다.
- **검증** — `./gradlew clean check` 를 실제 실행한다. 실행하지 않은 검증을 성공으로 보고하지 않는다.
  (통합 테스트는 Docker 필요 — 현재 환경에 Docker가 떠 있지 않다.)
- **평가 스크립트의 위치** — 채점·라벨링 도구는 프로덕션 소스에 넣지 않는다. 별도 디렉터리로 분리한다.
