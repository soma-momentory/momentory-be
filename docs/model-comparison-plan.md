## 0. TL;DR

현재 코드는 원본 문서의 **V1(LLM 프롬프트 모델)에 해당**하고, §4의 스키마·프롬프트 개편까지는
구현돼 있다. 그런데 **Notion 정본이 감정 택소노미 자체를 교체했다.** 코드의 `Emotion` 10종은
더 이상 정본이 아니다.

따라서 순서가 바뀐다. ⑴ **감정 택소노미를 새 12종으로 교체**하고(코드·프롬프트·평가 자산 전부),
⑵ 강도 척도를 0~4에서 1~3+판단 어려움으로 내리고, ⑶ 기존 대화 100건 공동 라벨링 파일럿을 돌린 뒤,
⑷ 동일 세트에서 V0·V1·V2를 비교한다.

**감정 흐름 유형은 여전히 범위 밖**이고, 원본 V4도 드롭 상태 그대로다.

히스토리 전문 유지, 평가 시 temperature 0.

## 1. 확정된 결정

1. **감정 흐름 유형(flow type)은 만들지 않는다.** 원본 문서의 Flow Type Macro F1 · Transition Macro F1 ·
   State Sequence Accuracy 지표와 A6 ablation은 전부 삭제. Notion 정본도 흐름 유형을 두지 않는다.
2. **버전 로드맵은 V0 → V1 → V2 → V3 네 단계.** 원본 V4는 존재 이유의 대부분이 흐름 유형이었다.
3. **V0 규칙 베이스라인은 필수다.** 라벨러가 2명이 되어 IAA 상한선은 잴 수 있게 됐지만, V0 없이는
   V1 숫자의 하한 좌표가 없다. 유지한다.
4. **평가 데이터는 두 갈래다.** 기존 대화 100건(Notion 정본의 파일럿)과 자체 생성 세트(§7.2)를
   함께 쓰되 **출처를 필드로 구분**한다. 자체 생성분의 결과는 **상대 비교용**이며 절대 성능
   추정치가 아니다 — 보고 시 반드시 명시한다.
5. **라벨러 2명, 독립 라벨링 후 조정.** 서로의 결과를 보기 전에 독립적으로 라벨링하고, 불일치
   원인을 유형별로 기록해 기준 문서에 환류한다. (구판의 1인 라벨 limitation은 해소됐다.)
6. **출력 스키마 확정이 라벨링보다 먼저다.** 라벨 스키마는 V1 출력 스키마와 1:1이어야 채점된다.
   **택소노미 교체(§3)가 스키마 확정의 선행 조건**이므로 라벨링보다 먼저 끝낸다.
7. **라벨링 대상은 대표 감정 12개까지다.** 세부 감정 60개는 사용자 선택 UI의 영역이고 정답 라벨을
   만들지 않는다. 모델 성능으로 세부 감정 분류 정확도를 보고하지 않는다.

### 2.2 Notion 정본 대비 빠진 것 (코드)

구판에서 지적한 누락은 `feat/emotion-extraction-v1` → `feat/model-comparison-eval` 에서 대부분
해소됐다. **정본 교체로 새로 생긴 격차**는 다음과 같다.

- **`Emotion` enum 10종이 통째로 다르다.** `ANXIOUS/DEPRESSED/ANGRY/FRUSTRATED/HAPPY/STUCK/
  LETHARGIC/TIRED/PROUD/CALM` → 정본 12종으로 교체해야 한다. 저장된 과거 세션·토픽의 감정 키
  마이그레이션 문제가 딸려 온다(§14.1).
- **`POSITIVE` 집합 재정의** — 현재 `HAPPY/PROUD/CALM`. 정본 기준으로는 기쁨·평온·뿌듯함·애정
  네 개가 후보다. 강점 기반 신호의 의미가 바뀌므로 `retro-chat-v2-plan.md` 와 함께 확인한다.
- **세부 감정 60개를 담을 자리가 없다.** 사용자 선택값은 `대표 + 세부(미선택 가능)` 두 필드로
  저장해야 하고, 사용자가 실제로 쓴 표현 원문은 그와 **별도 필드**로 보존한다.
- **강도 범위가 0~4다.** 정본은 1~3 + 판단 어려움.
- **`phase` 가 1급 필드로 채점된다.** 정본에서는 메모 수준으로 격하(§4.1).
- **명시적 감정 표현 감지 분기가 없다.** §5 신규.

## 3. 감정 체계 (정본)

대표 감정 12개는 그 자체로 선택할 수 있다. 더 구체적으로 표현하려면 해당 대표 감정 아래 세부 감정
하나를 고른다. 선택 가능한 감정은 총 72개다.

| 대표 감정 | 세부 감정 5개 |
|---|---|
| 기쁨 | 행복함, **고마움**, 신남, 설렘, 감동 |
| 평온 | 편안함, 안심, 홀가분함, 후련함, 담담함 |
| 뿌듯함 | 성취감, 보람, 자랑스러움, 만족감, 흐뭇함 |
| 애정 | 호감, 그리움, 애틋함, 정겨움, 반함 |
| 슬픔 | 서러움, 속상함, 외로움, 쓸쓸함, 상실감 |
| 불안 | 걱정, 초조함, 긴장, 두려움, 조마조마함 |
| 분노 | 짜증, 분함, 억울함, 배신감, 원망 |
| 실망 | 서운함, 아쉬움, 좌절감, 허탈함, 씁쓸함 |
| 부끄러움 | 창피함, 민망함, 쑥스러움, 무안함, 수치심 |
| 혼란 | 당황, 황당함, 난처함, 심란함, 막막함 |
| **미안함** | 죄송함, 죄책감, 후회, 자책감, 면목없음 |
| **지침** | 피곤함, 무기력, 소진, 귀찮음, 지겨움 |

**저장 규칙**

- `실망`을 고르면 → 대표 감정 = 실망, 세부 감정 = 미선택.
- `서운함`을 고르면 → 대표 감정 = 실망, 세부 감정 = 서운함.
- 사용자가 실제로 쓴 표현(`"서운했어"`)은 선택값과 **별도로 보존**한다.
- 대표 감정과 그 아래 세부 감정을 **서로 다른 감정 두 개로 세지 않는다.**

**출처와 한계**: 「한국어 감정단어의 목록 작성과 차원 탐색」의 단어 목록·평정 자료를 참고해 모멘토리
선택 화면에 맞게 재구성한 **설계안**이다. 해당 논문이 이 계층 자체를 검증한 것은 아니다.

**개정 이력**

- **2026-09-27 기쁨 세부: 즐거움 → 고마움.** 고마움은 원래 정본이 체계 밖으로 명시한 표현이었으나,
  AI Hub 사람 발화 1.7%로 애정(0.4%)·뿌듯(0.5%)보다 잦아 긍정 계열인 기쁨 아래로 옮겼다.
- **2026-10-01 대표 감정 미안함 추가(10 → 11종).** 미안함 3.2%·후회 2.9%·죄책감 1.9%로 애정·뿌듯의
  6~8배였다. 무엇보다 10종에 **'내 행동·선택에 대한 부정적 자기평가' 칸이 없었다** — 뿌듯함의
  반대짝이다. 부끄러움을 넓히는 안(B)은 수치심(시선)과 죄책감(행위)이 한 칸에 섞이고, 후회를
  실망에 넣는 안(C)은 실망의 정의("바깥에서 기대한 결과를 못 얻어")와 맞지 않아 기각했다.
  v2 골드 라벨이 0건인 시점이라 지금이 가장 싸게 바꿀 수 있었다.
- **2026-10-13 대표 감정 지침 추가(11 → 12종).** AI Hub 대화 58,268건 중 지치다·피곤·무기력·의욕 없음
  표현이 2.8%(우울 3.4% 별도) — 같은 방식으로 잰 미안·죄송 3.9%, 후회 2.9%와 같은 수준이고 질투 1.2%의
  두 배를 넘는다. 11종에 **에너지가 바닥난 부정 감정 칸이 없었다** — 평온의 반대짝이다(정서 척도 PANAS-X 도
  피로를 슬픔과 별도로 둔다). 1차 라벨링에서 "힘들다·피곤"이 슬픔으로 흡수되거나 보류로 빠졌고, 구 체계의
  `tired`·`lethargic` 이 갈 자리가 없던 문제(§14.1)도 이걸로 풀린다. 쉬는 행동 카드와 바로 이어진다.
  세부: 피곤함·무기력·소진·귀찮음·지겨움. 하루의 고됨으로 말한 피곤은 포함하고 통증 같은 몸 상태만이면
  감정으로 치지 않는다. **우울**은 슬픔/지침 중 문맥으로 고르는 모호 표현이다. 평가셋 라벨링 전이라 가장
  싼 시점이었다. **Notion 정본 반영은 대기 중이다.**

**체계 밖 표현**: 원래 정본이 예로 든 `고마움`·`미안함`·`죄책감`은 위 개정으로 체계 안에 들어왔다.
지금 남은 것은 `질투`·`혐오` 같은 표현이다. 어느 대표 감정의 세부로도 넣기 어려운 표현은
사용자 원문에 보존하고 **분류 체계 밖**으로 라벨링한다(§8.3). 사용자 테스트에서 자주 등장하면 감정
체계 개편을 검토한다.

### 3.1 혼동 기준 (라벨링·프롬프트 공통)

| 대표 감정 | 선택하는 경우 | 주요 구분 기준 |
|---|---|---|
| 기쁨 | 좋은 일·경험으로 기쁘고 즐거운 마음 | 자신이 해낸 일의 만족·보람이 중심이면 **뿌듯함** |
| 평온 | 편안하거나 긴장·부담이 풀린 상태 | 성취에 따른 만족이 중심이면 **뿌듯함** |
| 뿌듯함 | 자신의 행동·노력·결과에 만족하거나 보람 | 단순히 일이 즐거웠다면 **기쁨** |
| 애정 | 특정 대상을 향한 호감·친밀감·그리움 | 그 사람과의 좋은 일이 즐거웠다는 내용만이면 **기쁨** |
| 슬픔 | 상실, 외로움, 마음의 아픔·가라앉음 | 기대한 결과·반응을 못 얻은 게 중심이면 **실망** · 힘이 바닥나 의욕이 없는 게 중심이면 **지침** |
| 불안 | 앞으로 일어날 일·불확실한 상황을 걱정·두려워함 | 이해나 다음 행동 결정이 어려운 게 중심이면 **혼란** |
| 분노 | 부당함·침해·갈등으로 화·짜증·원망 | 기대에 못 미쳐 서운·허탈한 게 중심이면 **실망** |
| 실망 | 기대한 결과·관심·반응을 못 얻어 마음이 가라앉음 | 상실 자체로 아픈 게 중심이면 **슬픔** · 자기 선택을 탓하는 게 중심이면 **미안함** |
| 부끄러움 | 드러남·타인의 시선이 의식되어 창피·민망 | 갑작스러운 상황을 이해 못해 당황한 것이면 **혼란** · 내가 잘못했다·피해를 줬다는 게 중심이면 **미안함** |
| 혼란 | 예상 밖 상황의 이해·결정이 어려워 당황·심란·막막 | 앞으로의 결과가 걱정되는 게 중심이면 **불안** |
| **미안함** | 자신의 행동·선택이 잘못됐다고 느끼거나 남에게 피해를 줬다고 느낀다 | 남에게 **어떻게 보일지**가 중심이면 **부끄러움** · **바깥에서** 기대한 결과를 못 얻은 게 중심이면 **실망** · 상실 자체가 중심이면 **슬픔** |
| **지침** | 몸과 마음의 힘이 바닥나 지치고 의욕이 없다. 하루의 고됨으로 말한 피곤 포함 | 무언가를 잃어 아픈 게 중심이면 **슬픔** · 기대가 꺾여 허탈한 게 중심이면 **실망** · 통증 같은 몸 상태만이면 감정 아님 |

**두 감정의 근거가 각각 있으면 하나만 고르지 않고 둘 다 선택한다.**

**주시할 혼동 쌍**: 슬픔–실망, 불안–혼란, 분노–실망, 기쁨–뿌듯함, **부끄러움–미안함**(2026-10-01 추가 —
수치심과 죄책감은 심리학에서도 대표적으로 구분하는 쌍이다), **지침–슬픔·지침–실망**(2026-10-13 추가 — 우울,
좌절감·허탈함이 걸친다). 실망–미안함(아쉬움 vs 후회)도 지켜본다.
구판의 화남/답답/막막 경계는 **폐기**한다 — 답답·막막이 정본 12종에 없다. `eval/challenge/` 자산을
이 다섯 쌍 기준으로 다시 만들어야 한다(§14.3).

## 4. V1 재설계

### 4.1 출력 스키마

감정을 사건에 묶는다.

```json
{
  "events": [
    { "id": 1, "label": "회의", "summary": "회의에서 내 의견이 빠짐", "evidence": [1, 2] }
  ],
  "emotions": [
    { "eventId": 1, "raw": "내 의견만 빠져서 서운했어",
      "normalized": "disappointed", "intensity": 2,
      "evidence": "내 의견만 빠져서 서운했어", "evidenceIds": [2] }
  ],
  "keywords": [ { "label": "회의", "eventId": 1 } ]
}
```

- `events` 최대 2개.
- **`intensity` 는 1·2·3, 판단 어려움은 `null`.** (구판 0~4에서 변경. 이미 `Integer` 라
  역직렬화 호환은 유지된다 — §15 Jackson 주의사항 참조.)
- **`phase` 는 채점 대상에서 뺀다.** 정본은 "기본적으로 **사건 당시**의 감정을 라벨링한다"로 못박고,
  시점 차이는 판단 특성 메모로만 남긴다. 필드 자체는 `"그때는 화났는데 지금은 괜찮아"` 같은
  사례를 잡기 위해 **선택 출력으로 유지하되 지표에서 제외**한다.
- **`evidence` 는 두 곳의 뜻이 다르다** (§9.1 사건 정렬의 전제):
  - `events[].evidence` — 그 사건에 **속하는 사용자 발화 전체**(배정). **required.**
    사건 정렬 기준이자 Turn Assignment F1의 채점 대상이다. 근거 없이 뽑은 사건은 매칭에 실패해
    FP로 잡히는데, 이는 환각 사건에 대한 **의도된 페널티**다.
  - `emotions[].evidence` — 근거가 된 사용자 **문장 원문**. `emotions[].evidenceIds` — 그 문장의
    **발화 번호**(보통 1~2개), `events[].evidence` 의 부분집합.
  - 감정에 원문과 번호를 둘 다 두는 이유: 번호가 있어야 채점에서 기계적으로 대조하고, 원문이 있어야
    라벨링·일기 검증(Unsupported emotion rate)에서 사람이 바로 읽는다.
  - **Notion 정본은 근거를 "발화 원문"으로만 규정한다.** 발화 번호는 채점 재현성을 위한 리포 고유
    결정이며 정본과 충돌하지 않는다(원문은 그대로 둔다). 라벨링 시트에는 번호 열을 **추가**한다.
- 감정이 없으면 `emotions: []` — 억지로 채우지 않는다.
- **타인 감정**: V1은 사용자 감정만 출력한다. `"친구가 화가 났대"` 를 사용자의 분노로 옮기지 않는다.
  테스트 세트에 타인 감정 케이스를 넣어 **오탐률**로 측정한다.
- 세부 감정은 모델이 출력하지 않는다. **대표 감정까지만.**
- 흐름 유형 필드는 두지 않는다.

### 4.2 프롬프트에 넣을 규칙

- 「AI(바바)의 발화를 사용자 감정의 근거로 사용하지 않는다」
- 「사용자가 명시하지 않은 감정은 추측하지 않는다」
- 「근거는 반드시 `[U번호]` 로 지목한다」
- **「사용자가 부정한 감정은 선택하지 않는다」** — `"화난 건 아니고 서운했어"` → 실망만.
- **「사용자가 정정하면 정정한 표현을 우선한다」** — 다만 시간에 따라 둘 다 경험했다고 설명하면
  둘 다 출력한다.
- **「판단할 근거가 없으면 비워 둔다」** — 감정 정보가 없으면 `emotions: []`, 감정은 있으나 강도
  단서가 없으면 `intensity: null`. **기본값 2를 채우지 않는다.**
- **「12종에 억지로 맞추지 않는다」** — 체계 밖 감정은 `normalized` 를 비우고 `raw` 만 남긴다.

### 4.3 히스토리 처리

**비용은 자르는 이유가 못 된다.** 대화가 6턴 상한이라 히스토리가 무한정 자라지 않는다. 세션 끝 기준
전문 약 2,000자 ≈ 2,000토큰. 히스토리를 싣는 콜은 세션당 9번(G2×6 + G1·G4·G5)이고, 전문 대비 1200자
컷의 차이는 **약 2,000토큰 = 세션당 0.0002 USD**. 세션 전체가 0.002 USD 수준이므로 자르기는 그 10%를
아끼면서 사건 도입부를 버린다.

예산의 목적을 **"비용 절감"이 아니라 "폭주 방지"** 로 둔다.

| 콜 | 빈도 | 히스토리 정책 |
|---|---|---|
| G2 일기 턴 | 세션당 6회 | 예산 적용 — 최근 3턴 전문 + 그 앞은 슬롯 요약 |
| **G1 감정 · G4 일기 · G5 토픽** | **각 1회** | **전문 무삭제** |

추가로: ⑴ 프롬프트 조립 시 선택지 줄 제거, ⑵ **사용자 발화에만 번호 부여**(AI 질문은 번호 없이 남겨
근거로 지목 불가), ⑶ 자를 때는 앞이 아니라 중간을 자른다, ⑷ `TurnRequest.content` 에 발화 단위 상한.

```
[U1] 오늘 회의에서 내 의견만 빠졌어
(바바) 그때 어떤 기분이었어요?
[U2] 내 의견만 빠져서 서운했어
```

> ⚠ §9.3에서 비용이 **정식 선정 지표**로 올라갔지만 이 결론은 그대로다. 둘은 다른 축이다 —
> 여기는 "한 모델 안에서 히스토리를 자를 이유", 저기는 "모델 간 총비용 비교".

### 4.4 G1/G5 통합 (구현 완료)

G1이 사건·감정·**키워드**를 한 콜로 뽑고, 토픽은 그 결과에서 **LLM 없이 파생**시킨다. 같은 대화에 대한
감정 판단이 한 곳에서만 일어나야 채점이 성립한다.

**사건에 짧은 `label` 을 둔다.** `retrospect_topics.label` 은 누적 집계의 키(`idx_rt_user_label`)라
날마다 같은 일이 같은 이름으로 쌓여야 한다. `label` 이 비면 `summary` 로 대신한다.

**감정 물려주기 규칙** (토픽 파생, LLM 호출 없음):

| 토픽 | 감정 |
|---|---|
| 사건(SCHEDULE) | `eventId` 가 그 사건인 감정 |
| 사건이 **하나뿐**일 때 | 위 + `eventId` 가 빈 감정도 그 사건 것으로 본다 |
| 사건이 둘일 때 | 안 붙은 감정은 **어느 쪽에도 붙이지 않는다** |
| 키워드(KEYWORD) | 매인 사건의 감정. 매인 사건이 없으면 세션 전체 감정 |

**삭제한 것**: `TopicExtractor` 포트 · `GeminiTopicExtractor` · `ExtractedTopic` · `topicExtractPrompt`
· 토픽 응답 스키마 · `LlmRole.G5`.

⚠ **계측 축이 바뀐다** — `llm-usage` 로그에 `AI-G5` 가 나오지 않는다.

### 4.5 프롬프트 변형 스위치

`EmotionExtractor` 포트 아래에 변형만 enum으로 둔다: `ZERO_SHOT` / `FEW_SHOT` /
`FEW_SHOT_BOUNDARY` / `TWO_STAGE`(근거 발화 선별 → 감정 판단).

**`FEW_SHOT_BOUNDARY` 의 경계 예문을 새 혼동 쌍(슬픔–실망, 불안–혼란, 분노–실망, 기쁨–뿌듯함)으로
교체한다.** 구판의 화남·답답·막막 예문은 폐기.

**평가 시 temperature 는 반드시 0.** 0.7이면 버전 간 차이인지 노이즈인지 구분할 수 없다.

> ⚠ 프롬프트 예시와 평가 발화가 겹치면 지표가 부풀어 오른다(실측 3배). `PromptFactoryTest` 가 막는다.

## 5. 모델 호출 분기 (신규)

사용자의 **명시적 감정 표현 여부**에 따라 분석 모델을 고르는 방식을 실험한다.

| 단계 | 처리 |
|---|---|
| 명시적 표현 감지 | `"내가 서운했어"` 처럼 자신의 감정을 직접 표현했는지 판단. 부정·인용·타인 감정을 구분 |
| 감지됨 | 해당 유형에서 품질 기준을 충족하는 **저비용 모델** 호출 |
| 미감지·판별 어려움 | 간접 표현 유형에서 성능이 좋은 모델 호출 |
| 결과 통일 | 경로와 무관하게 사건·대표 감정·강도·근거·판단 보류를 **같은 형식**으로 출력 |

### 5.1 감지 방법 비교

| 방법 | 준비할 것 | 비용 특성 | 한계 |
|---|---|---|---|
| **감정 표현 사전·규칙** | 표현 목록, 부정·주체 판별 규칙 | 별도 LLM 호출비 없음 | 목록 밖 표현·복잡한 문맥을 놓침 |
| 기존 LLM으로 판정 | 판정 프롬프트 | 판정마다 API 호출비 추가 | 분석 전 비용·지연 증가 |
| 별도 분류 모델 학습 | 라벨 데이터, 학습·운영 환경 | 방식에 따라 다름 | 초기 구축 부담 |

**우선 감정 표현 사전·규칙으로 구현한다.** 단일 모델 방식과 비교해 **분기 오류를 포함한 전체 품질**,
비용, 응답 시간이 실제로 개선되는지 확인한다. 개선이 확인되지 않으면 분기를 넣지 않는다.

> ⚠ **미결: LangGraph.** Notion 정본은 이 분기를 "LangGraph에서" 구현한다고 쓴다. 현재 백엔드는
> Java/Spring Boot이고 `EmotionExtractor` 포트 하나로 정리돼 있다. LangGraph는 Python이므로
> ⑴ 별도 Python 서비스를 세우는 것인지, ⑵ 용어만 빌린 것이고 Java에서 분기할 것인지 결정이 필요하다.
> §14.4 참조. **결정 전까지는 Java 구현을 가정**하고 `EmotionExtractor` 앞단의 라우터로 설계한다.

### 5.2 사전·규칙의 판정 기준

`명시적 표현 = 있음` 은 **사용자가 사건 당시 자신의 감정을 감정 단어로 직접 표현**한 경우다.

| 사용자 발화 | 판정 | 이유 |
|---|---|---|
| "내 의견이 빠져서 서운했어." | 있음 | 자신의 감정을 직접 표현 |
| "결과가 걱정됐어." | 있음 | 자신의 감정을 직접 표현 |
| "처음엔 화났는데 나중엔 서운했어." | 있음 | 시점별로 직접 표현 |
| "내 의견만 빠졌어." | 없음 | 사건만 설명 |
| "친구가 서운했다고 했어." | 없음 | 타인의 감정 |
| "'서운하다'는 말을 들었어." | 없음 | 단어를 인용 |
| "화난 건 아니었어." | 없음 | 해당 감정을 부정 |

주체나 의미가 불명확해 두 라벨러가 일관되게 판정하기 어려우면 **판단 어려움**으로 표시한다.

**왜 V1 정답지로 못 쓰는가**

- **단일 라벨** — 대화 1건 = 감정 1개. 정본의 라벨링 단위는 **사건 × 감정**이고 복수 감정이
  전제다. Jaccard·다중라벨 Macro F1 채점이 성립하지 않는다.
- **강도·사건·근거 발화·명시적 표현 여부가 전부 없다.** v2 골드의 필수 항목이 통째로 빠진다.
- **대화 모양이 다르다** — 2~3턴이고 AI 질문이 회고 흐름이 아니다. 프로덕션 입력 분포와 다르다.
- **도메인 불일치** — 대인관계·건강/죽음·학교폭력/따돌림·재정 중심, 연령은 노년 31%.

**그래서 어디에 쓰는가**

1. **V0 규칙 베이스라인의 감정 어휘 사전** — 실제 한국어 감정 표현 50,676건이 정본 11종으로
   갈려 있다. 사전·규칙(§5.1)의 재료로 가장 값이 크다.
2. **V2 워밍업** — 파인튜닝 전 사전학습 자산.
3. **씨앗 하이브리드**(§7.3) — 실제 사람 발화 1문장을 씨앗으로 6턴 회고 대화를 만든다.
   순수 LLM 합성보다 말투가 자연스럽다.
4. **혼동 쌍 검증** — 슬픔–실망, 분노–실망 경계가 실제 발화에서 어떻게 갈리는지 확인.

변환 결과(`eval/data/aihub-v2.jsonl`)는 **커밋하지 않는다**(gitignore). 매핑표와 변환
스크립트만 리포에 둔다.

## 7. 평가 데이터 설계

### 7.1 기존 대화 100건 공동 라벨링 (정본 파일럿)

정본이 지정한 1차 작업이다. **iOS 출시(2026-09) 이후의 실사용자 대화를 쓴다.**

> 🔴 **동의 정비 전까지 시작할 수 없다.** 2026-09-27 `momentory.co.kr` 문서 대조 결과,
> 현행 처리방침·약관이 이 용도를 덮지 않는다 — §1 표의 `AI 회고·일기` 행 목적에 품질 개선이
> 없고, §3이 "자체 AI 모델의 학습 데이터로 사용하지 않습니다"를 명시하며, 약관에 이용 허락
> 조항이 없다. **방침·약관을 고치고 재동의를 받기로 했다**(2026-09-27 결정).
> 절차와 개정 문안 초안 → [`research-consent-rollout.md`](research-consent-rollout.md).
>
> 동의가 모이는 동안 **자체 생성 세트(§7.2)로 라벨링 기준을 먼저 다듬는다.** 10~20건으로
> 기준을 잡고 `eval/merge.py` 로 첫 IAA 를 보는 사이클은 지금 바로 돌릴 수 있다.
> 라벨링은 원문을 사람이 전부 읽는 작업이라 로깅보다 노출 범위가 넓다 — 동의 없이 만든
> 골드는 나중에 버려야 하고, 그때 날아가는 것은 수 시간~수십 시간의 작업이다.

- **한 사건에 관한 대화 묶음 = 평가 단위 1건.**
- **실제 참여자가 작성한 대화와 팀이 만든 가상 대화를 필드로 구분**한다. 섞어서 집계하지 않는다.
- **비식별화 후에만 라벨러에게 넘긴다.** `eval/dump.py --anonymize --pseudonymize` 가
  전화·이메일·주민번호·계좌·카드·URL·아이디를 가리고 세션 ID 를 해시로 바꾼다.
  **사람 이름은 자동으로 못 가린다** — `--review-names` 로 후보를 뽑아 사람이 검토한 뒤
  `--names` 로 다시 돌린다. 가명↔원본 ID 매핑(`--id-map`)은 **라벨 세트와 분리 보관**한다.
  자동 비식별화는 완전하지 않으므로 **라벨링 전 사람이 한 번 훑는 단계를 건너뛰지 않는다.**
- **기존 AI 결과를 사람에게 보여주지 않은 채** 두 사람이 독립적으로 라벨링한다.
- 두 사람의 판단이 다른 사례를 검토해 라벨링 기준을 보완한다.
- 부족한 감정, 간접 표현, 부정 표현 사례를 보충한다.
- **학습용·개발용·최종 테스트용으로 분리**하고, 같은 사용자나 같은 원본 대화의 변형본이 서로 다른
  묶음에 섞이지 않게 한다.

**진행 방식**: 먼저 **10~20건을 독립 라벨링**해 기준을 수정한 뒤 100건으로 확대한다.

**100건은 파일럿이다.** 최종 모델 선정에는 별도로 보존한 테스트 데이터를, 사용자 경험·개인화 평가에는
새로 수집한 사용자 확인값을 쓴다.

### 7.2 자체 생성 세트 (병존)

정본이 폐기한 것이 아니라 **파일럿 다음 단계의 본 데이터**다. 실사용 세션이 부족한 상황은 그대로다.

**화자 3명 확보(2026-09-02).**

| 세트 | 규모 | 만드는 법 | 라벨 |
|---|---|---|---|
| 자연 세트 | 45세션 (3명 × 15) | **실제 앱으로** 대화. 감정을 미리 정하지 않음 | blind, 2인 독립 |
| Challenge set | 60~80세션 | **정답을 먼저 정하고 생성**(by-construction) | 검수만 |

Challenge 가 희소 감정을 짊어진다. 자연 45세션이면 감정 인스턴스가 약 110개인데 자연 분포라 특정
감정에 쏠린다. 그래도 감정당 최소 기준(30)에는 못 미치므로 **희소 감정 F1 은 참고치이지 결론의 근거가
아니라고 보고한다** — 채점기가 감정별 `지원` 수를 함께 낸다.

**Challenge set 커버 영역 (정본 기준 재정의)**: 슬픔–실망 / 불안–혼란 / 분노–실망 / 기쁨–뿌듯함 경계,
타인 감정, 간접 표현, 부정 표현("화난 건 아니고 서운했어"), 정정 표현, **분류 체계 밖**(고마움·미안함·
죄책감), 감정 없음, 복수 사건, 사건 당시 vs 현재 시점 차이.

### 7.2.1 대화는 앱에서, 예측은 따로

- **대화는 실제 앱으로 받는다** — AI 질문이 진짜라 입력 분포가 프로덕션과 같고, `state_json` 에 남아
  덤프가 공짜다. 하루 1회 제한은 `userId` 기준이라 로컬 mock 로그인으로 계정을 나누면 된다.
- **예측은 나중에 temperature 0 으로 재실행한다** — 앱은 운영 설정(0.7). 분리해두면 같은 대화에
  프롬프트 변형을 여러 번 돌려 비교할 수 있다.

**V1은 학습이 없으므로 train/valid 분할이 필요 없다.** 정본 §7.1의 학습/개발/테스트 분리는 V2 진입
시점에 적용한다.

### 7.3 자체 생성의 한계와 완화

라벨러가 2명이 되면서 **라벨 편향은 상당 부분 해소**됐다. 남는 것은 **데이터 자체 생성** 편향이다.

- 지인 5~10명에게 각 8~10세션 부탁. 비공개 테스트 기간이라 연구 목적 사전 동의를 받기 좋다.
- 순수 LLM 합성은 자연 세트에 쓰지 않는다(생성·평가를 같은 Gemini로 하면 순환이 가장 심하다).
- 순환을 줄이는 장치: ⑴ 감정을 미리 정하지 않고 작성(자연 세트 한정), ⑵ 작성과 라벨링 사이 최소 1주,
  ⑶ `상황 키워드 × 목표 감정` 소재 매트릭스로 배분 — 배분표는
  [`material-matrix.md`](material-matrix.md) 에 있다. AI Hub 표적 수집으로 **뿌듯함 108 ·
  애정 40** 을 확보했고, **평온·부끄러움은 0 이라 전부 자체 작성**이다. 「혼자」 상황 열도
  통째로 비어 있다(상담 코퍼스에 없는 소재).

### 7.4 1차 학습셋·평가셋 (2026-10-02 확정)

> 데이터의 최종 목적은 공개 가중치 생성형 모델(Qwen3-8B 등) SFT 다(Notion 「AI 모델을 써야하는 이유」).
> 방향: **명시적 표현은 기존 LLM(또는 사전·규칙)이 맡고, 자체 모델은 간접 표현을 맡는다** — 정본
> 「AI 채팅 흐름 및 평가 설계」 §4 분기 구조. 「AI 모델을 써야하는 이유」의 비용 단락은 반대로
> 적혀 있어("검증된 사례는 전용 모델, 복잡한 사례는 기존 LLM") 맞춰야 한다.

**전제: 사람 시간 이틀**(2명 × 하루 5시간 ≈ 20시간). 사람이 다 하므로 시간에서 거꾸로 잡았다.

| 구분 | 건수 | 명시 | 간접 | 보류 | 복합·경계 | 라벨링 |
|---|---:|---:|---:|---:|---|---|
| 파일럿 | 20 | — | — | — | — | 2명 각자 → 조정 → 기준 확정 |
| 평가 | 200 | 60 (30%) | 120 (60%) | 20 (10%) | 위 셋 안에서 **최소 30건** | 2명 + 조정, LLM 초안 금지 |
| 학습 | ~500 | 10% | 85% | 5% | 위 셋 안에서 **최소 15%** | 1명 |

**두 축은 따로 다룬다.** 명시·간접·보류는 감정이 *어떻게 드러나는가*, 복합·경계는 감정이 *몇 개이고
헷갈리는 경계에 있는가*다. 한 대화가 양쪽에 동시에 속한다("뿌듯했는데 결과는 걱정돼" = 명시 + 복합).

| | 감정 1개 | 복합(2개 이상) |
|---|---|---|
| 명시 | "서운했어" | "뿌듯했는데 결과는 걱정돼" |
| 간접 | "내 의견만 빠졌어" | "무시당하고 결국 진료도 못 받았어" |
| 보류 | "친구가 약속을 취소했어" | — |

- **명시·간접·보류는 뽑을 때 나눈다(층화).** 사전으로 미리 가를 수 있다(보류는 AI Hub 에 거의 없어 직접 쓴다).
- **복합·경계는 뽑을 때 나눌 수 없다.** AI Hub 라벨이 대화당 감정 1개라 정보가 없고, 간접 복합은 사람이
  읽어봐야 안다. 그래서 라벨링하며 **표시**하고, 결과를 낼 때 따로 점수를 낸다. 다만 자체 모델이 차이를
  낼 핵심이라 최소 건수를 정해 두고 모자라면 채운다 — 명시 복합은 사전("서로 다른 감정 단어 2개 이상",
  AI Hub 8,787건), 경계는 AI Hub 대분류와 우리 감정이 엇갈리는 소분류(예: 슬픔 대분류의 "실망한"),
  간접 복합은 1차 라벨링 후 집계하고 모자라면 직접 쓴다.

**평가셋을 층화하는 이유 — AI Hub 분포는 자연 분포가 아니다.** 소분류 60개를 약 1,000건씩 균등하게
만들었고, 대분류 6개 중 5개가 부정 감정이며, 상담 대화다. 모멘토리 사용자의 실제 분포는 아직 모른다
(실사용 데이터는 재동의 전까지 못 본다). 그래서 평가는 **층별로 따로 점수를 낸다** — "명시에서 몇 점,
간접에서 몇 점"은 실제 비율과 무관하게 유효하다. 실제 비율을 알게 되면 층별 점수에 그 비율을 곱해 전체
점수를 다시 계산한다(평가셋을 다시 라벨링할 필요가 없다). 실제 비율은 재동의 후 실사용 대화나, 화자들이
앱에서 감정을 정하지 않고 쓴 대화(§7.2 자연 세트)로 추정한다.

**학습셋과 평가셋의 비율이 다른 이유.** 학습셋은 "무엇을 많이 배워야 하나"로 정한다 — 자체 모델이 맡을
간접을 85%로. 평가셋은 "층마다 몇 건이 있어야 점수를 믿을 수 있나"로 정한다 — 명시를 학습처럼 10%(20건)만
두면 "기존 LLM은 명시를 잘한다"는 전제를 20건으로 판단해야 해서 너무 흔들린다.

그 밖:
- 명시 10%(학습)는 분기 감지기가 잘못 넘긴 명시적 대화에 대비하는 안전판이다. 표적 수집 결과를 재사용한다.
- 각 층 안에서는 감정이 고르게 나오도록 뽑는다(AI Hub 라벨 기준 — 25% 정확도라 1차 라벨링 후 모자란
  감정을 겨냥해 2차를 뽑는다). 애정은 AI Hub 라벨에 아예 없어 층화로도 못 채운다.
- 같은 가상 인물은 최대 2건, 평가와 학습은 서로 다른 인물에서 뽑는다(AI Hub 가상 인물 3,449명).
- 앱 형식(6턴) 대화 직접 작성은 이틀 범위에서 뺐다 — 평가가 AI Hub 대화 기준이라는 한계로 남긴다.
- LLM 초안은 1일차에 쓰지 않고 속도를 보고 2일차에 정한다. 쓰더라도 운영 모델과 다른 모델로, 평가셋에는 금지.
- 다음 규모는 학습곡선(150 → 300 → 500)으로 정한다.

## 8. 라벨링 절차

> **라벨링 실무 기준서의 정본은 Notion
> [「모멘토리 감정 라벨링 기준 초안 v0.2」](https://app.notion.com/p/v0-2-3e8b5a896e42804aabcac826749cd64d)
> 이다.** 여기에는 리포 작업에 필요한 만큼만 옮긴다. 기준을 고칠 때는 Notion을 먼저 고친다.

### 8.1 라벨링 단위

- 한 사건에 관한 사용자 대화 묶음 = 1건.
- 한 대화에서 다른 사건을 이야기하면 사건별로 나누고, 같은 사건을 여러 턴에 걸쳐 설명하면 하나로 묶는다.
- **AI 발화는 문맥 파악에만 쓰고, 라벨 근거는 사용자 발화에서 찾는다.**
- **기본은 사건 당시의 감정**이다. 채팅하는 현재 감정과 구분한다.
  `"그때는 화가 났는데 지금은 괜찮아."` → 사건 당시 감정은 **분노**.

### 8.2 대표 감정 선택 규칙

1. **한 사건에 여러 감정을 선택할 수 있다.** `"발표를 마쳐서 뿌듯했는데 결과는 걱정돼"` → 뿌듯함 + 불안.
   각 감정에 **뒷받침하는 사용자 발화가 있어야** 한다. 사건만 보고 추측해 추가하지 않는다.
2. **부정한 감정은 선택하지 않는다.** `"화난 건 아니고 서운했어"` → 실망만.
3. **정정하면 정정한 표현을 우선한다.** 다만 `"처음에는 화났고 나중에는 실망했다"` 처럼 시간에 따라 둘 다
   경험했다면 **둘 다 선택하고 시점을 메모**한다.
4. **타인의 감정을 사용자 감정으로 옮기지 않는다.**

### 8.3 판단 불가 3종 (구분해 기록)

| 상태 | 기준 | 예시 |
|---|---|---|
| 감정 정보 부족 | 사건은 있지만 감정 근거가 없음 | "오늘 발표했어." |
| 대표 감정 판단 어려움 | 감정은 있으나 어느 범주인지 불분명 | "기분이 복잡했어." |
| **분류 체계 밖** | 감정은 분명하나 12종 어디에도 안 맞음 | "친구가 잘되는 게 질투가 났어." |

**가장 가까워 보이는 것을 억지로 정답으로 만들지 않는다.** 분류 체계 밖 사례는 따로 모아 감정 체계
개편 여부를 판단한다. **채점에서는 '감정 없음'(정답 = 빈 배열)과 '판단 불가'(채점 제외)를 구분**한다.

### 8.4 강도 기준

강도는 사건 전체가 아니라 **선택한 대표 감정 각각**에 부여한다.

| 값 | 기준 | 예시 |
|---|---|---|
| 1 — 약함 | 약하게 느꼈다고 표현하거나 크게 신경 쓰이지 않았다고 말함 | "조금 아쉬웠어." |
| 2 — 보통 | 감정이 분명하고, 약하거나 매우 강하다는 단서 없음 | "결과가 아쉬웠어." |
| 3 — 강함 | 매우 강한 감정을 명시하거나, 그 감정 때문에 행동·집중에 큰 영향 | "너무 화가 나서 하던 일에 전혀 집중하지 못했어." |
| 판단 어려움 | 대표 감정은 골랐으나 강도 근거가 부족 | 맥락만으로 감정을 추정하고 강도 단서는 없는 경우 |

**2와 판단 어려움의 경계**: `"서운했어"` 처럼 감정을 분명히 표현하고 강도 단서가 없으면 **실망 2**.
사건만 설명해 실망을 조심스럽게 추정한 경우는 **판단 어려움**.

판단 순서:

1. 사용자가 직접 설명한 강도와 이후의 정정을 우선한다.
2. `조금`·`엄청` 같은 단어를 **부정·완화 표현까지 포함한 문장 전체**에서 해석한다.
3. 행동·일상에 미친 영향은 **그 감정 때문이라고 연결될 때만** 쓴다.
4. 감정의 지속 시간과 사건 당시의 강도를 구분한다.
5. 반복 언급·문장 길이·느낌표 개수만으로 강도를 높이지 않는다.

```
"엄청 화난 건 아니고 조금 짜증이 났어."  → 분노 1
"엄청 화났지만 금방 풀렸어."            → 사건 당시 분노 3
```

### 8.5 라벨러 간 의견 조정

두 사람은 서로의 결과를 보기 전에 **독립적으로** 라벨링한다. 이후 불일치를 다음 순서로 검토한다.

1. 각자 선택한 대표 감정과 근거 발화를 나란히 확인한다.
2. 불일치 원인이 **사건 구분 / 대표 감정 / 강도 / 명시적 표현 여부** 중 무엇인지 기록한다.
3. 현재 기준으로 해결되면 합의한다.
4. 같은 유형이 반복되면 **Notion 기준 문서에 정의와 예시를 추가**한다.
5. 사용자 발화만으로 해결할 수 없으면 **합의 어려움**으로 남긴다.

특히 **슬픔–실망, 불안–혼란, 분노–실망, 기쁨–뿌듯함**에서 얼마나 갈리는지 확인한다.

### 8.6 pre-annotation 정책

- **자연 세트·기존 100건: blind.** 기존 AI 결과를 보여주지 않는다.
- **Challenge set: by-construction 라벨 + 사람 검수.** 생성 결과가 의도와 어긋나는 경우가 반드시
  나오므로 검수를 건너뛰지 않는다. Challenge set으로 **Macro F1 절대값을 주장하지 않는다.**
- 시간은 pre-annotation이 아니라 **도구**로 줄인다 — `eval/labeler.html` 이 대화를 `[U1]`,`[U2]` 로
  렌더하고 감정/강도/근거를 클릭으로 찍어 JSON을 뽑는다. **정본 택소노미·강도로 갱신 필요**(§14.3).

### 8.7 라벨링 시트 열 구성

| 열 이름 | 입력 예시 |
|---|---|
| 대화 ID | `C001` |
| 사건 ID | `C001-E01` |
| 사건 요약 | 회의에서 내 의견이 빠짐 |
| 사용자 대화 원문 | 해당 사건에 관한 사용자 발화 |
| **사건 배정 발화 번호** | `[1, 2]` — *리포 추가 열*, §9.1 정렬·Turn Assignment 채점용 |
| 라벨러 ID | `A` |
| 대표 감정 | 실망 |
| 감정별 강도 | 실망 2 |
| 감정 근거 발화 | "내 의견만 빠져서 서운했어." |
| 강도 근거 발화 | "서운했어." |
| 데이터 출처 | 실참여 / 가상 — *리포 추가 열*, §7.1 |
| 명시적 표현 여부 | 있음 |
| 판단 특성 | 없음 (부정·정정·인용·타인 감정·시점 차이·복합 감정 등) |
| 라벨링 상태 | 확정 가능 / 의견 조정 필요 / 정보 부족 |
| 불일치·검토 메모 | 필요할 때 작성 |

**필수 정답은 대표 감정과 감정별 강도다.** 세부 감정 60개를 위한 열이나 정답은 만들지 않는다.
사용자 발화 원문을 보관하면 이후 선택 화면을 검증할 때 표현을 다시 확인할 수 있다.

**사람이 붙인 라벨 / AI 추정값 / 사용자 자기보고값은 서로 다른 필드로 저장한다.**

### 8.8 드리프트 방지

2인 라벨링으로 완화됐지만 여러 날에 나눠 하면 기준이 흔들린다.

1. **순서 랜덤화** — 감정별로 몰아서 라벨링하지 않는다.
2. **배치 시작마다 앵커 예문 재확인.**
3. **마지막 일관성 패스** — 전체를 감정별로 재정렬해 훑는다. 이 패스에서 바꾼 라벨 수가 드리프트 지표다.

### 8.9 기준 설정

```
V0 (하한)  <  목표 기준  <  IAA (상한)
```

라벨러가 2명이 되면서 **IAA를 상한선으로 쓸 수 있다.** 감정 집합은 Krippendorff's alpha,
강도는 가중 카파로 측정한다. 원본 문서의 "임의로 0.8처럼 정하지 말라"를 지키는 방식이다.

재라벨링(자기 일치도)은 IAA를 대체하지 않지만, **1주 간격 재라벨 20건**은 개인 드리프트 점검용으로
유지한다.

## 9. 평가 지표

원본 문서의 **흐름 관련 3종은 삭제**했고, 정본 반영으로 **시점(phase) 지표도 뺐다**.

### 9.1 사건

- Event Count Accuracy · Event Detection F1
- Turn Assignment Macro F1 (근거 발화 번호로 채점)
- Event Summary Score — BERTScore + 사람 평가 (ROUGE 부적합)

**사건 정렬 규칙: `events[].evidence` 발화 번호 집합의 Jaccard(IoU).**

요약 의미 유사도(BERTScore·임베딩) 대신 근거 겹침을 쓰는 이유:

| | 근거 발화 IoU | 요약 의미 유사도 |
|---|---|---|
| 재현성 | 결정적 — 집합 연산 | 임베딩 모델 버전에 따라 점수가 변함 |
| 자의성 | 임계값 하나 | 임계값 + 모델 선택 |
| 설명력 | "발화 2,3이 겹쳐서 같은 사건" | "유사도 0.81이라서" |
| 표현 차이 | 요약이 달라도 근거가 같으면 매칭 | 강함 |
| 근거 오류 | 근거를 잘못 달면 실패 | 영향 없음 |

**채점이 또 다른 모델에 의존하기 시작하면** 나중에 "V2가 V1보다 낫다"는 결론이 임베딩 모델 탓인지
해명해야 한다. 채점은 결정적일수록 좋다.

**알고리즘**

1. 사건이 최대 2개이므로 **전수 탐색으로 IoU 합이 최대인 이분 매칭**을 찾는다(경우의 수 2가지).
2. **IoU 임계값 미만인 쌍은 매칭하지 않는다.** 짝 없는 예측 = FP(환각 사건), 짝 없는 정답 = FN(누락).
3. **Event Count Accuracy 는 정렬 없이** 개수만 비교한다.

**임계값**: 기본 **0.5**. 자의적일 수밖에 없으므로 파일럿에서 **0.3 / 0.5 / 0.7 민감도를 함께 보고**한다.
확인할 것은 절대값이 아니라 **임계값을 바꿔도 버전 순위가 뒤집히지 않는가**이며, 뒤집히면 그 자체가
보고할 발견이다.

**요약 유사도 보조 매칭은 지금 넣지 않는다.** 파일럿에서 "근거는 안 겹치는데 명백히 같은 사건"이 몇 건
나오는지 세고, 유의미하게 많을 때만 추가한다.

### 9.2 감정 — 두 수준에서 따로 채점

`emotions[].eventId` 때문에 감정 채점이 사건 정렬에 얹히면, 점수가 나빴을 때 감정 판단이 나쁜 건지
정렬이 나쁜 건지 구분할 수 없다. 분리한다.

**세션 단위 (사건 무시) — 주 지표.** 정렬과 완전 독립.

| 지표 | 확인할 내용 |
|---|---|
| **Macro F1** (대표) | 12개 감정 각각의 F1 평균. 일부 감정을 계속 놓치는지 |
| Micro F1 | 전체 사건·감정에 대한 전반적 분류 성능 |
| Jaccard | 감정 집합 겹침 |
| 감정별 정밀도·재현율 | 특정 감정을 과잉 제안하거나 누락하는지 |
| 감정 간 혼동표 + 감정별 이진 혼동행렬 | 혼동 쌍 4종을 직접 확인 |
| 라벨 개수 오차, Hamming Loss | 과잉·과소 출력 경향 |
| **명시적·간접 표현별 F1** | §5 분기가 맡을 입력에서 각 모델이 실제로 잘 작동하는지 |
| **근거 적합률** | 제시한 사용자 발화가 그 감정을 뒷받침하는지 |

**사건 단위 (정렬 후) — 보조 지표.** **Event Attribution Accuracy**: 정렬에 성공한 사건 쌍에 한해,
감정이 올바른 사건에 붙었는가. 그리고 **사건별 감정 집합 일치율**(한 사건의 복수 감정 목록을 모두 맞혔는지).

> **모델이 대표 감정만 추정하므로, 세부 감정 60개의 분류 정확도를 모델 성능으로 보고하지 않는다.**

### 9.3 강도

사람이 판단한 강도와 AI 강도를 **사건 × 감정** 단위로 비교한다.

| 지표 | 확인할 내용 |
|---|---|
| 정확 일치율 | 1·2·3을 정확히 맞힌 비율 |
| MAE | 평균 절대 오차 |
| **2단계 오차율** | 1을 3으로, 3을 1로 판단한 비율 |
| 가중 카파 | 등급 순서를 반영한 일치도 |
| **판단 보류율·적절성** | '판단 어려움'을 얼마나 자주, 적절하게 쓰는지 |
| **응답 비율** | 전체 평가 대상 중 강도를 실제로 제시한 비율 |

**강도를 제시한 쉬운 사례만 골라 정확도를 보고하지 않는다. 응답 비율과 강도 오차를 함께 제시한다.**

### 9.4 그 밖

- **주체** — 타인 감정을 사용자 감정으로 잡은 **오탐률**.
- **신뢰도** — ECE, Brier Score, Coverage × Selective Accuracy.
- **5줄 일기 (감정 모델과 분리 평가)**
  - 자동: BERTScore, Entity/Fact Consistency, Source coverage, Unsupported claim rate
  - 사람: 충실도·순서·관점·자연스러움 1~5점
  - **최우선: Unsupported emotion rate** — 근거 없는 감정을 일기에 추가한 비율

### 9.5 비용과 응답 시간 — 정식 선정 지표

표시 단가가 아니라 **같은 평가 대화에서 실제로 쓴 토큰과 호출 횟수**를 기준으로 비교한다.

| 지표 | 포함 범위 |
|---|---|
| 분석 1건당 평균 API 비용 | 명시적 표현 감지 호출 + 분석 모델 호출 + 재시도 호출 |
| **95백분위 분석 비용** | 특히 긴 대화에서 발생하는 높은 비용 |
| 1,000건당 예상 분석 비용 | 운영 규모 환산 |
| 평균·95백분위 응답 시간 | 일반적인 대기 시간과 느린 사례 |
| **채팅 1건당 총 API 비용** | 대화 생성 호출(G2×6, G4) + 마지막 감정 분석까지 전부 |

**모델 선정 원칙 (구판의 가중합 종합점수를 대체한다)**

> **감정 누락률과 강도 오차에 대해 먼저 품질 기준을 정하고, 그 기준을 충족하는 후보들 사이에서
> 총비용과 응답 시간을 비교한다.**

분기 방식은 **감지기가 잘못 분기한 사례까지 포함**해 단일 모델 방식과 비교한다. 개발 단계에서는
지표를 합치지 않고 **버전 × 지표 성능표**를 유지한다.

## 10. 사용자와 연결한 지표 (신규)

| 시점 | 비교 기준 | 확인할 질문 |
|---|---|---|
| 출시 전 오프라인 모델 비교 | 사람이 대화문을 읽고 붙인 라벨 | 모델이 글에 드러난 감정을 제대로 읽는가? |
| 사용자 테스트 | **AI 결과를 보기 전에** 사용자가 고른 감정·강도 | AI 제안이 사용자의 경험과 맞는가? |
| 개인화 검증 | 해당 사용자의 이후 대화에서 받은 확인값 | 과거 개인 사례를 참고하면 실제로 개선되는가? |

**사용자 테스트에서는 AI 결과를 보여주기 전에 사건 당시의 감정과 강도를 선택받는다.**
AI 제안을 본 뒤의 수정 행동은 별도로 기록한다.

| 지표 | 정의 |
|---|---|
| 사용자 감정 누락률 | 사용자가 사전에 고른 감정 중 AI가 제안하지 않은 비율 |
| 사용자 감정 확인 일치율 | AI 제안을 사용자가 **명시적으로** 확인한 비율 |
| 감정 추가·삭제·변경률 | 사용자가 제안을 어떻게 수정했는지 |
| 사용자 강도 정확 일치율·MAE | AI 강도와 사용자가 사전 선택한 강도의 차이 |
| 강도 수정 방향 | AI가 사용자보다 낮게/높게 추정하는 경향 |
| 세부 감정 도달률 | 원하는 세부 감정을 화면에서 찾아 확정한 비율 |
| 확인 부담 | 확인 소요 시간, 요청 횟수, 중도 이탈률 |

> ⚠ **결과 화면을 그냥 넘긴 행동을 명시적 동의로 간주하지 않는다.** 화면 전환과 "맞아요" 선택을
> 서로 다른 이벤트로 기록해야 한다 — **현재 코드에 이 구분이 없다**(§14.2).

사용자 자기보고값은 개인화·UX 평가의 기준이지, 감정을 완벽하게 측정한 절대적 정답이 아니다.

## 11. 개인별 감정 강도 추정 (신규)

**처음부터 사용자마다 모델을 따로 학습시키지 않는다.**

1. **초기** — 공통 강도 기준으로 감정별 강도를 추정한다.
2. **확인값 수집** — 초기 일부 대화에서 사용자가 사건 당시 강도를 직접 선택한다. AI 추정값과 사용자
   확인값을 구분해 저장한다.
3. **개인 사례 참고** — 이후 대화 분석 시 그 사용자가 확인한 **과거 유사 사례를 참고자료로 제공**한다.
   **현재 대화의 맥락을 우선한다.**
4. **효과 검증** — 과거 사례를 참고해 이후의 새 대화를 예측한다.
   **평가 대상 대화의 정답을 과거 사례 입력에 포함하지 않는다.**

| 개인화 지표 | 비교 방법 |
|---|---|
| 감정 일치율 개선폭 | 개인 사례 사용 시 − 공통 기준 |
| 강도 MAE 개선폭 | 공통 기준 − 개인 사례 사용 시 |
| 사용자별 개선·악화 비율 | 평균 개선 뒤에 가려진 사용자별 차이 |
| 추가 비용·응답 시간 | 과거 사례 입력으로 늘어난 토큰과 대기 시간 |

**금지**: MBTI에 따라 강도를 일괄 조정하지 않는다. 한두 개의 과거 사례로 사용자의 표현 성향을
확정하지 않는다. 개인화 후에도 강도는 **"대화에 표현된 감정 강도에 대한 추정"** 으로 안내한다.

   → **자체 생성 세트(§7.2)로 지금 시작할 수 있다.** 실사용자 대화는 동의 정비가 끝난 뒤
   합류시킨다 — [`research-consent-rollout.md`](research-consent-rollout.md).
5. **기존 대화 100건 공동 라벨링 파일럿** — 데이터 상태와 헷갈리는 사례를 확인한다.
6. **파일럿을 끝까지 한 바퀴** — 라벨링 → V1 실행 → **채점 스크립트 실행까지**. 숫자가 나오는 데까지 간다.
7. **V0 베이스라인 구현.**
8. **모델 비교** — 같은 평가 데이터에서 감정 성능, 강도 성능, 판단 보류, 비용, 응답 시간. §9.

10. **프롬프트 변형 비교** (§4.5) → V1 최종 확정.
11. **사용자 테스트** — AI 결과를 보여주기 전 자기보고를 받고, 이후 확인·수정 행동을 기록. §10.
12. **개인화 검증** — 과거 확인 사례가 이후 대화의 사용자 일치도를 높이는지 **추가 비용과 함께** 판단. §11.
13. **V2 착수** — AI Hub 워밍업(§6.1) + Momentory 파인튜닝.

리드타임이 길어 오히려 먼저 시작하는 게 맞다. **라벨링만** 택소노미·스키마 확정 이후로 미룬다.

## 14. 미결 / 리스크

### 14.1 과거 감정 데이터 마이그레이션 (신규, 최대 리스크)

`Emotion` 10종 교체는 **저장된 데이터를 건드린다.** `retrospect_topics` 의 감정, 스냅샷 `state_json` 의
`normalized`, `confirmedEmotions`, 주간 리포트 집계가 전부 구 키(`depressed`·`frustrated`·`stuck`·
`lethargic`·`tired`)를 담고 있다. 결정할 것:

- 구 키 → 신 키 매핑을 만들 것인가, 과거 데이터를 "구 택소노미"로 표시해 집계에서 분리할 것인가.
- 매핑한다면 `frustrated`(답답) · `stuck`(막막)은 정본 **혼란** 쪽에, `depressed`(우울)은 **슬픔**,
  `tired`(피곤) · `lethargic`(무기력)은 2026-10-13 신설한 **지침**으로 간다. 그래도 우울은 슬픔/지침 중
  문맥이 필요해 무손실 매핑은 여전히 아니다.
- 주간 리포트·감정 통계 화면이 과거·현재 키를 섞어 보여주면 사용자에게 드러난다.

**권고: 매핑하지 않고 택소노미 버전 필드를 붙여 분리 집계한다.** 무손실이 아닌 매핑은 나중에
"이 통계가 뭘 센 건지" 해명할 수 없게 만든다. **결정 필요.**

### 14.2 `confirmedEmotions` UX·저장 구조

§10 사용자 연결 지표 전체가 이 값에 의존하는데 현재 구조로는 못 쓴다.

- 후보가 LLM 추출 감정 **4개로 제한**(`distinctNormalized(...).limit(4)`) → 사용자가 고르고 싶은
  감정이 후보에 없을 수 있다. 정본은 12종 전체 + 세부 60을 전제한다.
- 선택이 **`limit1` 로 1개만 저장** → 정본의 복수 감정 선택과 충돌.
- **화면 전환과 "맞아요" 선택이 구분되지 않는다** → 사용자 감정 확인 일치율을 잴 수 없다.
- **AI 결과를 보기 전 자기보고**를 받을 자리가 흐름에 없다(정본 §7 사용자 테스트 전제).

UX 변경을 수반하므로 `retro-chat-v2-plan.md` 와 함께 결정한다. **§10·§11 착수의 선행 조건.**

### 14.5 그 밖

- **세부 감정 60개의 사용자 검증** — 비슷한 선택지를 사용자가 구별할 수 있는지, 목록 밖 감정이 얼마나
  자주 나오는지 확인해야 한다(정본 §9의 1번 항목). 라벨링과는 별개 작업이다.
- **강도 1~3이 실제로 재현 가능한 기준인지** 파일럿 전까지 알 수 없다. 구판 0~4를 3단계로 줄인 것이
  정본 결정이므로, 가중 카파가 낮게 나오면 **앵커 예문 보강**으로 대응한다(더 줄일 수 없다).
- **V2 학습 단계의 사용자 단위 분할** — 화자 3명으로는 70/15/15를 못 나눈다.
  **leave-one-user-out 3-fold 교차검증**으로 간다. 기존 대화 100건이 합류하면 재검토한다.
- ~~**AI Hub 국외 반출 해석**~~ — 2026-10-03 가능하다는 답을 받았다(§6.1.1). 답변 원문을 남기는 일만 남았다.
- **애정·뿌듯함 데이터 부족** — AI Hub가 못 덮는 두 감정(§6.1). 소재 매트릭스로 의도적으로 채운다.

## 15. AGENTS.md 준수 (구현 시)

구현 착수 전 `momentory-be/AGENTS.md` 를 다시 확인한다. 이 계획에 특히 걸리는 조항:

- **API 계약 변경은 승인 필요** — **택소노미 교체는 응답에 드러나는 계약 변경이다**(감정 키 문자열이
  바뀐다). `ReplyDto`·일기/토픽 응답·주간 리포트를 확인하고 **승인 없이 진행하지 않는다.**
  `TurnRequest.content` 의 `@Size` 도 요청 검증 강화 = 계약 변경이므로 별도 승인 대상이다.
- **인터페이스 최소화** — 프롬프트 변형은 `EmotionExtractor` 구현체를 늘리지 말고 **enum + PromptFactory
  분기**로 처리한다. §5 라우터도 포트를 새로 파기 전에 기존 이음매로 되는지 본다.
- **Flyway** — 감정 스키마 확장은 `state_json` 안이라 마이그레이션 불필요. 다만 **§14.1 택소노미
  버전 필드**는 컬럼이 필요할 수 있다. 이미 적용된 마이그레이션은 절대 수정하지 않는다.
- **역직렬화 호환** — 실측(Jackson 3): **모르는 필드는 조용히 무시**되지만 **빠진 primitive 는 실패**한다
  (`Cannot map null into type int`). 새 필드는 **참조 타입(List·Integer)** 으로 둔다. `intensity` 가
  이미 `Integer` 라 1~3+null 로 바꿔도 구버전 스냅샷이 열린다.
  `RetrospectStateCodecTest#deserializesPreEventSnapshot` 이 회귀를 막는다.
- **OpenAPI** — 응답 DTO가 바뀌면 계약 테스트와 `/v3/api-docs` 를 함께 갱신·검증.
- **테스트** — 택소노미 교체는 `Emotion` 파싱, 토픽 파생, 주간 리포트 집계에 광범위하게 걸린다.
  기존 테스트의 감정 상수를 기계적으로 치환하지 말고 **의미가 유지되는지** 확인한다.
- **검증** — `./gradlew clean check` 를 실제 실행한다. 실행하지 않은 검증을 성공으로 보고하지 않는다.
- **평가 스크립트의 위치** — 채점·라벨링 도구는 프로덕션 소스에 넣지 않는다. `eval/` 에 둔다.
